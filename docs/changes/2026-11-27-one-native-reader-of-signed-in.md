title: The phone has one native reader of "signed in", the voice's gate
class: red
---
What: station E6.2 of `docs/design/phone-sign-out-and-server-client-in-exact-2026-11-27.md`. Deleted the native readers of "is this phone signed in" that pages could see: `ChoirSignIn.signedIn`; the `signedIn` field of `ChoirPlayerView` (the `choirPlayer` source keeps its other fields: `pl.playing` is read); the `signedIn` field of the bar facts (`BarFacts`, `BarInfo`; nothing read it); the sign-in guard in `ChoirApp.refresh` (it only warms the computer id, and `ChoirEnvironment.warm` already checks for a key); the `choirRefresh` send and its two uses in `account.contract` (`finishAuth`, and the unused action `refreshRadio`); the module's `keystate` op and its Keychain read (`ModelsModule.keyState`). Shared code's host probe ("is the app module here", `host.ts`) now asks `mailCan` (answers `{ok: true}` in `MailSeal.reply`, reads no key; Android's module refuses it, as it refused `keystate`). What stays native: `TurnGate.keyPresent` (the voice's gate, the one native reader), `ChoirClient`'s own key read per request, and, outside this station, `MailSeal`'s default `KeychainKeyStore.keyRemains()` and the sign-out sequence's key-id compare and read-back in `ModelsEntry.swift` (E6.6). Pages learn "signed in" from `choirAuth` (`account-state.ts`) only. Native-boundary gate: 3,080 to 3,066 lines, 16 to 15 interface names.

Why: several readers could disagree with each other and with shared code (a locked phone read as absent by one and unreadable by another). In production shared code never read the native `keystate` (it reads the Exact secret store), so the op was only a presence probe that also read the Keychain.

Proof: `one-signed-in-reader.test.ts` R1 to R3 failed before the change and pass after (R4, a native that says nothing about the key is "unreadable", passed before and is kept); `host.test.ts` and `bar.test.ts` updated. Seen: whole `bun test` 1841 pass, 0 fail; `bun exact.mjs contract build app.contract` ok; `bun exact.mjs test web` 35 ok, 2 fail (the two kokoro tests of `voices.test.contract`, failing on origin/main too); `swift test` in `mobile/AutoradioKit`: 863 tests, 0 failures, 2 skipped (`MailSealTests/testK3TwoFirstUsesAtOnceShareOneKey` skipped on purpose, it hangs intermittently). The Swift lines deleted are proved by the compile and the existing suites only; `ModelsEntry.swift` and `AutoradioModule*.swift` are not built by the package tests (they compile in the app build), so those edits are unbuilt. Nothing was run on a device.

Replaced: `ChoirSignIn.signedIn`, `ChoirPlayer.signedIn`, `BarFacts.signedIn`, `choirRefresh`, the native `keystate` op.

Undo: revert the commit. Behaviour that can differ: no connection warm-up after a sign-in finishes (the first voice turn, or the first shared request that writes `choir.computer-id`, finds the computer then); a launch warm-up still runs (`AutoradioModule` init).
