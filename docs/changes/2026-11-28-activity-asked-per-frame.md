date: 2026-11-28
title: Activity's source is asked when its inputs change, not every frame
class: orange
---
What: the Activity source (`act` in `mobile/AutoradioLab/members-settings.contract`) no longer takes the date after `with`. It took `stime.epochAtZero + performanceNow()` there, which is a new number at every frame, and Exact asks a source again whenever a `with` value changes (`contract-grammar.md`, "A change to either asks again"). So the app asked `/api/changelog?limit=50&minor=1` about 42 times a second from launch, and signed out it still called the source every frame. Now the source (`activityPage` in `activity.ts`) takes only sign-in, the Refresh tick, the computer's state and the native facts. Each row carries its own time (`at`) and a fixed UTC stamp ("2 Jan, 03:04"). The age ("5 minutes ago") is made where the row is drawn, by the contract function `agoText` in `activity.contract`, from the row's time and Exact's date read there (`stime.epochAtZero + performanceNow()`). The rule from 2026-11-27 stays: no age is shown until `exactTime` has answered (`stimeKnown`). `act` also has `when pg.top.startsWith("activity:")`: it is read only by the Activity page, so nothing is asked until that page is on top, and each time it opens the feed is asked afresh. The age text is the same as before. One consequence: an age on screen is worked out when the row is drawn, so it moves on at the next draw, not on its own.

Why: measured 2026-11-28 on a signed-in iOS simulator, plain launch, 159 s: 6,643 requests to the changelog with the Activity page closed. The same fault ran on the web test host signed out: 845 calls to the source in about 16 seconds of test time before, 3 after (open, Refresh, and the first answer). Cause: change 2026-11-27 "Activity's clock is Exact's, not a native fact" passed a date that differs at every ask. The other resources were checked: no other `with` exists in the contracts, and no other resource reads the clock.

Proof: `exact-facts.test.ts` H1 and H3 fail on the old code (the source still returned `ago`; the contract had `with ...performanceNow()`) and pass now; H3 also fails any resource line that reads `performanceNow()` or `epochAtZero`. The count above is from a throwaway log in the web host's source handler, removed afterwards. `activity.test.contract` (page opens only when asked for, stands while the clock moves, Refresh keeps it answered) passes. `agoText` was run in a small scratch app: 30 s and 100 s read "a minute ago", 5 and 58 minutes read minutes, 4,000 s reads "an hour ago", 7,300 s reads "2 hours ago", a day old or ahead of the clock shows the UTC stamp, a zero time and an unknown date show nothing. That scratch app is not in the repo. Whole `bun test` and `bun exact.mjs test web` as in the commit's report (the two `voices.test.contract` failures are as on main). Not proved on a device: that the request rate falls to one, that ages read right on the Activity page, and that a signed-in page shows rows when opened. The web host has no account, so no row has been drawn by a test.

Replaced: the `with` date and the `known` and `now` arguments of `activityPage`; `ago` on each row (now `stamp`); the TypeScript `when()` age rule (the contract function replaces it).

Undo: revert the commit. The old behaviour comes back, with its request storm.
