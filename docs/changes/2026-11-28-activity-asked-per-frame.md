---
date: 2026-11-28
title: Activity's source is asked when its inputs change, not every frame
class: orange
---
What: the Activity source (`act` in `mobile/AutoradioLab/members-settings.contract`) no longer takes the date after `with`. It took `stime.epochAtZero + performanceNow()` there, which is a new number at every frame, and Exact asks a source again whenever a `with` value changes (`contract-grammar.md`, "A change to either asks again"). So the app asked `/api/changelog?limit=50&minor=1` about 42 times a second from launch, and signed out it still called the source every frame. Now the source (`activityPage` in `activity.ts`) takes only sign-in, the Refresh tick, the computer's state and the native facts. Each row carries its own time (`at`) and a fixed UTC stamp ("2 Jan, 03:04"). The age ("5 minutes ago") is made where the row is drawn, by the contract function `agoText` (`ago/ago.contract`; the `ago/` folder is a test fixture app around that production file, and nothing builds the fixture into the app), from the row's time and Exact's date: `stime.epochAtZero` plus the page's clock `actNow`. `actNow` is one number for the whole page, written from `performanceNow()` when the Activity page opens, on Refresh, and every 30 seconds while the page is on top (two gated tasks, `change(...)` and `every(30000, ...)`, in `members-settings.contract`). No row reads `performanceNow()`, so rows are not redrawn per frame, and `actNow` is never named by a resource. An age on screen is therefore at most 30 seconds old, and it moves on when the clock does. The rule from 2026-11-27 stays: no age is shown until `exactTime` has answered and the clock is set. `act` also has `when pg.top.startsWith("activity:")`: only the Activity page reads it, so nothing is asked until that page is on top, and each open asks afresh. The age text is the same as before, case by case, with one difference on purpose: a row that arrived between two steps of the page clock is up to a minute ahead of it, and now reads "a minute ago" (it would have shown its UTC stamp); a row more than a minute ahead keeps the stamp.

Why: measured 2026-11-28 on a signed-in iOS simulator, plain launch, 159 s: 6,643 requests to the changelog with the Activity page closed. The same fault ran on the web test host signed out: 845 calls to the source in about 16 seconds of test time before, 3 after (open, Refresh, and the first answer). Cause: change 2026-11-27 "Activity's clock is Exact's, not a native fact" passed a date that differs at every ask. The other resources were checked: no other `with` exists in the contracts, and no other resource reads the clock.

Proof: `exact-facts.test.ts` H1 and H3 failed on the old code and pass now. H3 is a pin, not an analyser: every non-test contract line that reads `performanceNow` or `epochAtZero` is listed in the test, so a new or changed clock line fails until someone checks where its value goes; and no resource declaration (read whole, over several lines, strings and comments stripped) names a listed clock name (`actNow`, `mkT`, `mkSince`, `mkFrom`, `mkPressAt`, `mkCloseAt`, `mkHot`, `mkIdle`, `now`) or the clock itself. H3b tests that name check on small snippets (caught in arguments, `with`, `when` and over several lines; not caught for a string, a field or another resource). `agoText` has 25 cases in `ago/app.test.contract` (unknown date, 0, the one-day floor and 1 ms above it, a future time, rows 1 ms, 59 s and 61 s ahead, 0, 59, 119 and 120 seconds, the millisecond edges 59999, 60000, 119999, 3599999, 7199999 and 86399999, 59 min 59 s, 1 h, 1 h 59 min, 2 h, 23 h 59 min, 1 day, older). `ago.test.ts` works each out by a copy of the old TypeScript `when()` and finds no difference except the two rows just ahead of the clock, which differ on purpose and are named in the test. It also runs the fixture under Exact's web host when Exact is present. `activity.test.contract` shows the clock unset before the page opens, set at open, unchanged at +1 s and +29 s (a per-frame clock fails), moved at +31 s, and set again by Refresh. The request count (845 calls to the source in about 16 s of test time before, 3 after) came from a throwaway log, since removed. Whole `bun test` and `bun exact.mjs test web` as in the commit's report (the two `voices.test.contract` failures are as on main).

Not proved: in CI, which has no Exact checkout, `ago.test.ts` only checks the expected texts against the old code's answers; the contract function itself runs only where the Exact checkout is (the lead runs it before landing). Not proved on a device: that the request rate falls to one, that ages read right on the page, and that a signed-in page shows rows. The web host cannot see the source asked again on Refresh (signed out it answers at once, so only the tick is shown), and it has no account, so no row has been drawn by a test.

Replaced: the `with` date and the `known` and `now` arguments of `activityPage`; `ago` on each row (now `stamp`); the TypeScript `when()` age rule (the contract function replaces it); a date read in every row's view.

Undo: revert the commits. The old behaviour comes back, with its request storm.
