What: the phone's sign-out now closes the voice before it deletes the key, and a turn cannot outlive it. One gate, `TurnGate`, holds all its sign-out state under one lock and never calls out to the key store while deciding: a flag (sign-out has begun and its sequence has not ended) and an epoch that moves once per sign-out. The flag is shut synchronously, as the first statement, by the module's native sign-out op (`ModelsEntry.swift`, before any hop) and again, idempotently, by `ChoirApp.signOut`. `LabRuntime.closeVoiceForSignOut` then ends the engine's listening and turn inside one actor turn before any await (`TurnEngine.endForSignOut`: hands-free off, enrolment tap cleared, turn and pipeline cancelled, voice cut), drops a take in hand, and moves the session off the microphone, bounded to 2 s: a move that fails (`SessionCoordinator.reapply` now says so, including when another caller's move failed first) or does not answer is not waited for, and the microphone is closed the direct way (`LabRuntime.stop`, which the next play or question starts again through `ensureEngine` / `startRequest`). Only then the old steps run, in main's order: playback stops, shared code gets up to 5 s to post that it left the air with the old key still held, the key is deleted, the wipe runs. Every turn entry (typed, hands-free commit, button) captures the epoch and asks again at the last points before anything leaves the phone: after its waits, in `runTurn`, at the start of the pipeline, after the position is read, before the desk request, before each write to the conversation and each hand-off to speech. The turn's epoch also travels with every request its tasks make (a task-local set where the pipeline starts), and `ChoirClient.request`, the one native key read, reads the key under the gate's lock and refuses a request of an older epoch, so an old turn that reaches it after a fast sign-out and a new sign-in cannot go out under the new account's key; a request no turn made is refused while a sign-out runs. The places that open the microphone refuse while the flag is up: `HandsFreeSwitch.set(true)` (the one path to "on", checked under the switch's own lock, which sign-out's `set(false)` also takes, so a take's give-back that races sign-out cannot reopen it), `SessionCoordinator.setRecordingTake(true)`, `TakeSession.start` (at entry and after each await), `TurnEngine.handsFreeSet(true)` and the enrolment tap. A second `signOut` joins the running one; the end of the sequence and the clearing of the task slot are one step under the app's lock, so one that arrives at the end cannot leave the gate shut. Not changed, kept exactly as on main: the key is deleted and the wipe runs unconditionally, so a sign-in that lands while a sign-out runs is destroyed with the old one (problem record, item 5); where the key lives; shared code's sign-out.

Why: after the first round (afd7d78ff) three reviews found the rest: a take's give-back reopened the microphone, a turn suspended in a wait resumed past an entry-only check, a take could start during sign-out, an old turn's request could carry a later account's key, and a gate that remembered who left could stick shut. This round removes what would not be correct: natively there is no event that says a key was stored (a sign-in is shared code writing the Exact secret, `keepKey` in `app-signin.ts`; native's ops are `signOut`, `wipe`, `accountStores` and the read-only `keystate`), so the gate keeps no copy of "who is signed in" and no identity: after the sequence ends, whether a turn goes is what the module's `keyPresent` reader says, as on main. The supersede rule of the second round (delete only the key sign-out began with) is removed: it left the old account's native stores readable by the new account and made shared code drop the old key's pending revoke. A kill leaves: before the key is deleted, signed in with the microphone off (hands-free is never kept across a launch) and shared code's pending marker finishes the sign-out; after it, signed out, and the marker finishes the wipe.

Proof: `SignOutOrderTests`, 32 tests, order observed through one sequence shared by the key store, the session owner, the desk and the voice. Failing before this round (seen on the previous commit): a take started during the wait (recording, session on the microphone), a take suspended in the permission prompt, a take suspended in the radio's yield (microphone left on), a stale `handsFreeSet(true)`, the enrolment tap set during sign-out. Written to fail only under a mutation, because the previous code already held them: suspended in `addressing.decide`, suspended in `holder.retrieve`, an answer suspended in its apply step, a second sign-out from the last callback (the previous code's stuck gate), the epoch-bound request and the epoch reaching the desk (these two use new API and could not run on the old code). Mutation check, tests that fail with one part removed: the switch's refusal (give-back, yield); the take guards in `start` alone (permission prompt, yield), the coordinator's refusal alone (nothing: `start` still stops it), both (the take started during the wait); the pipeline-body guard alone, or with the one after `position()` (nothing: the guard before the desk request and the client's check still stop it), all three together (the addressing test); the re-check before the desk request alone (nothing: the client's check stops it), with the client's check removed too (the retrieval test, the epoch-bound request test); the client's check alone (the bound-request test, the no-native-request test); the element check in the answer loop alone, or the two checks before the writes alone (nothing: the other stops it, and the loop runs on the engine's actor so the window between them is a flag set from another thread, not testable), both (the apply-step test and the answer test); the stale `handsFreeSet(true)` refusal, the enrolment-tap refusal, the epoch in the client's read, the task-local binding (the desk-epoch test), the end of the sequence under the app's lock (five tests), `reapply`'s memory of a failed move (the direct-close test). Whole suite through the lock: 859 executed, 2 skipped, 0 failures, run with `--skip MailSealTests/testK3TwoFirstUsesAtOnceShareOneKey` after that test hung once at 0% CPU (the known flake). The native non-voice count holds at the ceiling, 3082 lines. Left open, not fixed here: (a) a request that read the key just before the gate shut still goes out with the old key; it is bounded by the cancellation of the turn's tasks (the awaited `session.bytes(for:)` is cancelled with its Swift task, `ChoirClient.postEventStream`) and the server revoke of the old key is shared code's, made after sign-out; (b) after the sequence ends there is no native copy of "who is signed in", so a stale write of the old key would count as a key present; (c) a take's yield suspended across a whole sign-out opens the microphone briefly when it resumes, and gives it back at once; (d) a stale `setHandsFree(true)` or give-back that runs after the sequence has ended, with the key gone, is refused only by the key-present reader. Not proved on a device: on a phone, sign out while it is listening, while it is answering, and while a take is recorded.
