## 1. Findings

**Size and churn.**
- vmctl is 10.8k non-test lines and vmmanager 4k.
- The largest files are `ownership.go` (3014), `manager.go` (3427) and `handlers.go` (1834).
- `OwnershipRegistry` has about 90 methods behind one mutex.
- 108 commits in 90 days.
- 50+ problem docs mention vmctl (recovery 14, liveness 11, release 9, resources 7, contracts 4, security 4).

**Diagnosis.** Every panelist verified four structural faults in code.

1. **Uncertainty resolves to destruction.** A guest that cannot be proven alive *and* healthy can be killed by many paths, and none of them records who asked. Destructive sites today:
   - `bootVM`:
     - orphan cleanup by `/proc` cmdline scan, with no pid file needed (`manager.go:662-673` → `:1999-2014`);
     - pid-file fallback (`:2028-2039`);
     - `forceCleanup` of a tracked non-running instance (`:665-666`).
   - Readiness-timeout kills in boot and resume (`manager.go:860-865`, `:1048`).
   - `RecoverVMWithConfig` / `RefreshVMWithConfig` kill the tracked process (`manager.go:1358`, `:1394`). Resolve reaches recover through `ensureActiveVMReady` → `recoverOrRestartActiveVM` once a health failure outlasts a 45-second grace (`ownership.go:1100-1121`, `:1432`).
   - `HibernateVM`, a kill with a label (`manager.go:923-944`). Its error is ignored, and the state is persisted anyway (`ownership.go:2386-2389`).
   - `StopVM`, and `reapUnmanagedLocked` from stop and logout under `r.mu` (`host_capacity.go:215-235`).
   - Process reconcile:
     - a process **with no ownership row is reaped on the second sweep tick**, about 2 minutes;
     - an owned untracked process is reaped after a 10-minute grace (`host_capacity.go:149-181`);
     - neither checks busy-ness.
   - Pressure reclaim: busy protection of ephemeral (example.com / example.test) computers **expires after `MaxBusyProtect` = 2 h** (`host_capacity.go:291-320`; `node-b.nix:765-767`). These are exactly the Gate 2 QA computers.
   - `DestroyVMState` kills an untracked guest before deleting its directory (`manager.go:1251-1273`). Retention prune reaches it.
   - Manager shutdown can stop every guest (`manager.go:564-574`). It is off in production, but its default is dangerous (`VMCTL_STOP_MANAGED_ON_EXIT` defaults to true, `main.go:141`).

   **The burden of proof is backwards.** Adoption needs pid file + live process + one health probe, has no cmdline check, and then sets `Healthy=true` (`manager.go:1113-1159`). A kill needs only a cmdline match.
2. **Five facts are collapsed into health probes:** alive, ready, busy/quiescent, route-authorized, and permitted-to-stop. Adoption, degradation, busy-ness and reap each use separate HTTP probes, and each treats a failed probe as permission. `guestBusy` **fails open**: a transport or decode error means "not busy" (`ownership.go:2835-2846`).
3. **Guest process lifetime is coupled to the controller.**
   - The Firecracker children live in vmctl's cgroup (`KillMode=process`, `node-b.nix:677`).
   - The console is forwarded through a vmctl-owned writer (`manager.go:1725-1731`, `:1909`, `:1930-1934`).
   - On load, vmctl demotes Booting/Active/Degraded/Stopping ownerships to `Stopped/"vmctl-restart"` (`ownership.go:526-531`). That is crash semantics applied to a computer that never restarted.
   - It reattaches serially before the port opens (`main.go:202-226`).
   - **Restart count per deploy:**
     - Host-OS deploys restart vmctl twice. `switch-to-configuration` restarts it because `vmctlExec` embeds the store path (`node-b.nix:67-75`), then the explicit restart runs (`ci.yml:1351-1353`).
     - Pointer deploys skip the switch but restart services themselves (`ci.yml:1177-1184`, `1277-1302`).
4. **Too many actors hold destructive authority.** These can each cause a stop, kill, refresh or disk swap, with no common operation serialization:
   - resolve, recover, refresh, cold-recover and stop/logout/remove;
   - the sweeps (idle, pressure, retention, process reconcile, warmness, platform warm);
   - the proxy (`runComputeRecovery`: wake error → refresh, `compute_status.go:592-594`; refresh on booting, degraded, failed, or **any single unreachable probe**, `:633-640`);
   - **the browser**: three failed bootstrap probes, where a timeout or a 503 counts as one, fire cold-recover (`Desktop.svelte:927-983`). Cold-recover stops the VM, quarantines `data.img` and boots replay-only (`cold_recover.go:532-583`).

   `StopVM`, `HibernateVM` and `ResumeVM` take `m.mu`, not the per-VM `lockVMOperation` (`manager.go:902-963`).

**Secondary faults:**
- **Locks held across I/O.** `bootVM` holds the global `m.mu` across mkfs/resize2fs, the credential disk, ip/iptables execs and launch (`manager.go:652-847`). The registry holds `r.mu` across stop/hibernate kills (`ownership.go:2242-2258`, `2368-2386`).
- **Persistence failures are only logged** (`ownership.go:553-556`). Ownership removal ignores stop errors (`:2313-2321`).
- **Network setup swallows errors and continues** (`manager.go:1872-1881`, `3177-3254`).
- **Cold recover is a synchronous HTTP saga.**
- **Unrelated jobs live in vmctl:**
  - the runtime-package server and autoputer reverse proxy, which includes a hidden platform-computer ensure (`handlers.go:1227-1500`);
  - pulse and auth-db account classification;
  - retention GC by email domain.
- **72 `VMCTL_*`/`VM_*` env names.**

**Corrections the panels made to my earlier claims** (all verified):
- There is no `Manager.StartVM`, and `bootVM` is not the only chokepoint.
- `ResumeVM` is live: the platform-computer warm path uses it (`platform_computer.go:75`).
- `ResolveOrAssignDesktopContext` has a production caller (`handlers.go:349`).
- The `mgr==nil` branches are generic guards, not a deletable backend.
- The tests *can* represent a live untracked process (`host_capacity_test.go:32-52`, `:290-311`). What is missing is real-process, latency and cross-caller coverage.
- CI's active-computer refresh runs only on a manual dispatch (`ci.yml:880`, `1423-1434`).
- A durable lifecycle-intent store already exists: corpusd `lifecycle_control` (`internal/platform/lifecycle_control.go:63-149`), prepared by the proxy (`computer_lifecycle.go:119-134`). It has only pending/completed fates.
- A planned-restart marker already exists:
  - written and fsynced by `agentcore/planned_restart.go:41-73`;
  - consumed at guest boot before actors start (`autoputer/run.go:526-539`);
  - fields: reason, target and timestamp, with a 15-minute expiry;
  - no operation, epoch or boot binding.
- On 10-10, every reattach failure was a health skip (55 skipped, 0 route-refused).
- The 09:25:48 kill's caller is **unattributed**. The proxy refresh-on-unreachable is the most plausible path (hypothesis).
- microvm.nix builds the guest image. Its runner was declined for good reason: per-VM Nix evaluation and dynamic networking (`flake.nix:425-431`). Its host pattern of a systemd unit per VM is what this plan reuses.

## 2. Converged plan

**Thesis.**
- **Destruction requires a positive, attributable, authorized reason. Uncertainty never supplies one.**
- **A guest process does not share fate with its controller.**

The panel added a third rule:
- **Protecting an uncertain guest must be bounded and visible.** Otherwise "uncertainty resolves to destruction" becomes "uncertainty resolves to invisibility": a wedged guest becomes immortal while admission refuses everyone else (deepseek; glm; muse).

### 2.1 Target shape

1. **Observations are separate facts, and unknown fails closed.** The four facts are:
   - `process`: identity-verified via cmdline/pidfd *and* VMID + realization epoch from the launch descriptor (later from systemd `InvocationID`);
   - `ready`: from the guest;
   - `quiescent`: from a guest-granted lease only;
   - `route-authorized`.

   Unknown is never idle and never dead. Adoption never manufactures `Healthy=true`.
   - A **guest-pushed heartbeat** over the tap is *required observation*. It carries VM, epoch, work generation, running_runs, desk_pending and selfdev_active, and is bound by `bindRequestToGuestComputer`. It exists so stranded or wedged guests are visible and capacity is diagnosable.
   - A heartbeat is never stop authority.
2. **Stop authorization is the only gate to a destructive effect.**
   - Every effect in §1.1's inventory routes through `Stop(vmID, Authorization)`. That includes kill, refresh, recover, hibernate, destroy, readiness-timeout cleanup and orphan reap.
   - Allowed authorizations:
     - owner stop or destroy;
     - an owner-confirmed maintenance recovery;
     - a guest-granted idle lease, for idle, update-at-idle and capacity;
     - an explicit disposable-manifest disposition for test and QA computers. A missing ownership row is **not** authorization.
   - Boot returns `AlreadyRunning` or `ErrLiveUnmanaged`. It never kills.
   - **Receipt stages.** Authorization is persisted before action, dispatch is recorded, and the observed outcome is recorded. Each stage binds ComputerID, VMID, realization epoch, process or invocation identity, operation id and caller. Receipts go to an append-only JSONL under `vm-state/receipts/`, never the whole-file rewrite.
   - A caller-supplied reason string is evidence, not authority.
   - Kernel OOM, host shutdown and external kills are recorded as *observed* deaths.
3. **Idle lease and planned-restart marker, designed as one protocol.**
   - **The lease.** It is:
     - granted by the guest after it atomically closes admission for *all* work sources and checks its obligations;
     - bound to ComputerID, realization epoch, work generation, operation id, nonce and purpose, with a short expiry;
     - single-use;
     - kept with admission closed through the stop.

     A stop-commit check re-verifies the generation just before acting. If the lease expired or was cancelled, the stop aborts, and on expiry the guest reopens admission.
   - **The marker.** Extend the existing `planned_restart.go` marker rather than inventing a host-only one. Add operation id, source realization, target release or CodeRef, and the host `boot_id`. The executor installs it, and the guest acknowledges it durably *before* the stop.
   - **Consumption.** The marker is consumed before any work and cleared on cancel or failure. A mismatched target, a changed `boot_id` or a stale marker means crash semantics.
   - A consumed marker is never recreated by retrying an old operation.
   - Old guests that cannot grant a lease are **never automatically stopped**. The bound is admission (5) plus an owner-visible state.
4. **One per-computer executor, imperative and durable, with observational reconciliation.** One actor per computer serializes realize, stop, update-at-idle and maintenance-recover.
   - **Removes:** `pendingWaiters`, `refreshing` and the independent boot paths.
   - **No lock across I/O.**
   - **Recording.** Operations are recorded in phases, and corpusd `lifecycle_control` gains `failed` and `interrupted` fates. It stays the canonical owner-intent store; vmctl's journal is operational only.
   - **On controller restart,** the executor *observes* what an issued effect actually did: the systemd job, invocation, exit, receipt. It records that, and never blindly replays it.
   - **Restart classes.** It distinguishes four:
     - controller restart, which must not interrupt a running guest;
     - guest-runtime restart;
     - VM crash;
     - host reboot.
   - **No perpetual `want=running`.**
5. **Capacity by bounded admission.**
   - **Reservations.** Atomic memory reservations at admission count:
     - live legacy children;
     - adopted, unready and in-flight realizations;
     - Firecracker overhead;
     - host-service headroom.

     Protected classes reserve rather than bypass, and a missing sample refuses rather than admits (today: `host_capacity.go:256-270`).
   - **When full,** the result is a typed `capacity-unavailable` plus an owner-visible list of what holds capacity and why. Stranded or unresponsive guests surface as "computer unresponsive: restart?", which leads to an owner-confirmed maintenance stop. A timeout escalates *visibility*, never destruction.
   - **Pressure reclaim and the busy cap** are disabled first, then deleted.
6. **systemd owns guest processes** (Phase 1, spike-gated). Each guest runs from a template unit `choir-vm@<vmid>.service`.
   - **Template settings:**
     - `restartIfChanged=false` and `stopIfChanged=false`;
     - not `wantedBy` anything, so a host reboot starts nothing;
     - `Restart=no`;
     - an explicit `Slice=`, with class slices carrying `MemoryLow` and OOM order, or per-instance `set-property`, chosen in the spike;
     - `MemoryMax` = guest RAM + VMM overhead.
   - **Launch.** The unit `exec`s Firecracker from an **immutable, digest-bound per-realization launch descriptor**, which is never rewritten while that realization lives.
   - **Network.**
     - A fail-closed `ExecStartPre` network helper takes its exact allocation from the descriptor.
     - The helper uses `iptables -w` and rolls back partial failures, fenced to its own realization.
     - `ExecStopPost` tears down only its own tap and rules.
   - **Console.** Output goes to the unit journal or a bounded per-VM file, independent of vmctl.
   - **Privilege.** vmctl stays root and talks to systemd over D-Bus. Running vmctl non-root with polkit is a later, separate red step; Phase 1 does not claim it.
   - **Fallback.** Transient units (`systemd-run`) if template property injection fails.
   - **Migration.** New realizations use units, and legacy children keep their current supervision. **`KillMode=process` and the legacy adapter stay until vmctl's cgroup holds only vmctl.** Removing them is its own verified step, and the guests' `MemoryLow` moves to the slice before the first unit-launched guest. Migration never stops a guest just to move it.
7. **Deploys publish; computers adopt at idle.**
   - One vmctl restart per deploy, by removing the store path from the unit text or setting `restartIfChanged=false`, plus one explicit restart.
   - Restart is harmless once item 6 lands.
   - Guest updates are pending releases, applied only through item 3.
   - CI never refreshes running computers.
8. **vmctl does lifecycle and route projection only.**
   - Move out:
     - the package server and reverse proxy to the proxy or artifact layer, keeping CodeRef verification and guest binding, and removing the hidden platform ensure;
     - pulse and account classification to ops;
     - retention to a fenced GC worker that uses disposable manifests and never kills (start and delete are fenced together).
   - Fold the platform computer into an always-on class, migrating its `ResumeVM` caller first.
   - Route CAS stays the sole writer (doctrine). Process adoption never depends on it, and route-DB calls run with short contexts outside the executor and registry locks.
   - One typed, validated config replaces the env sprawl.
9. **Package layout** follows *who mutates what under which lock*, about 600 lines per file:
   - `internal/vmctl/{registry, resolve, executor, stopauth, admission, routeauth, httpapi}`
   - `internal/vmmanager/{units, launchspec, network, disk, epoch, console, legacy}`
   - `internal/vmpolicy`, which only submits operations
   - `internal/vmgc`

   A file split alone is **not** a fix.

### 2.2 Order of operations

Each step gets its own problem doc, red ceremony, Landing Loop and staging proof. No code push lands while a self-development rerun is in flight.

**Phase 0: disarm and instrument.** Order matters, so each step is its own commit.

1. **Kill receipts** at every site in §1.1's inventory: caller, cause, epoch, observations. This lands *first*, alone, so the next destructive caller is attributable. That matters because the 09:25:48 caller is still unknown.
2. **Disarm the escalators.**
   - Browser: delete the automatic cold-recover. It shows typed pending and unresponsive states instead.
   - Proxy: delete wake→refresh and refresh on booting/degraded/failed/unreachable.
   - Resolve: alive-but-unready returns pending, never `RecoverVM`.
3. **Close the automatic destructive paths.**
   - `bootVM`, recover and refresh refuse over a live process (`ErrLiveUnmanaged` → `guest_reattach_pending`).
   - Readiness timeout records a failure and does not kill.
   - `DestroyVMState` refuses an alive or unknown process.
   - Reconcile reaps nothing that is alive, and no-row processes need a disposable-manifest disposition.
   - Disable the `MaxBusyProtect` expiry and pressure reclaim of live guests.
   - `guestBusy` fails closed.
4. **Bounded admission and strand visibility** (§2.1.5), before or together with step 3, so protection cannot become host OOM.
5. **Adopt by identity, alive-unready.** It does not claim healthy, and routing is gated on readiness.
6. **Restart hygiene.**
   - One restart per deploy.
   - Discovery is bounded and parallel, with per-computer inventory-pending fencing before any realization.
   - Health can be reported before inventory completes.
7. **Safe deletions:** `VMCTL_ALLOW_HOST_PROCESS`, `ForceKillVM`, `MarkFailed`, and the `STOP_MANAGED_ON_EXIT=true` default flipped to false. Wrappers, `mgr==nil` guards and `ResumeVM` wait for their callers to migrate.

**Phase 1: systemd units for new realizations.**
- A spike on one disposable QA computer comes first.
- Legacy children keep their supervision until drained.
- Removing `KillMode=process` and the legacy adapter is a later, separately verified step.

**Phase 2: per-computer executor, journal and observational reconciliation, plus the lease, marker and heartbeat protocol.**
- Port verbs one at a time.
- The lifecycle_control fates are extended.
- **No automated stop or update-at-idle is enabled until the lease exists.** Until then, stops come only from the owner, maintenance, or disposable manifests.
- `ownership.go` splits along the executor.

**Phase 3: enable lease-gated idle stop and update-at-idle.**
- Delete pressure reclaim, `guestBusy`-as-authority and the "hibernate" label.
- Hibernate means stop until real snapshot exists.

**Phase 4: move the non-lifecycle jobs out, and finish the file splits and config consolidation.**

**Later:** real Firecracker snapshot/restore (API socket, not `--no-api`). It applies only to lease-idle guests, and never as crash-work resumption.

### 2.3 Acceptance (E2E on staging, per CLAUDE.md, phase-specific)

`scripts/vmctl_lifecycle_probe.mjs` (operator tooling) runs on disposable QA computers and writes a retained JSON artifact. Each phase must pass its rows.

| Scenario | Must hold | Phase |
|---|---|---|
| Two vmctl restarts ~20 s apart while a guest runs a long desk turn and while another is mid-boot | epoch, data.img digest and in-flight run unchanged; tap/iptables intact; no kill | 0 |
| Guest slow to answer health during restart; probe storm from browser and proxy | no refresh and no cold-recover fired; typed pending state reaches the browser | 0 |
| Concurrent wake/recover/refresh | at most one operation; no kill; every effect has a receipt naming its caller | 0 |
| Admission at capacity with a stranded guest | typed refusal; owner-visible holder list; no reap | 0 |
| Host-OS switch that changes the guest template | every guest's `InvocationID` unchanged | 1 |
| vmctl killed mid-boot, mid-stop and mid-update | observed outcome recorded; nothing replayed; no guest work interrupted | 2 |
| Markerless crash / one planned resume / crash during resume | close / resume once / close (no second resume) | 2 |
| Idle stop with a busy guest; lease expiry; replayed lease | refused / admission reopens / refused | 3 |
| Unauthorized recovery vs authorized maintenance | no kill vs exactly one stop | 0–3 |

### 2.4 Adjudicated disputes

| Dispute | Ruling | Why |
|---|---|---|
| Process authority: systemd units vs per-VM shim vs microvm.nix runner vs keep the Go supervisor | systemd template units, with transient units as the spike fallback | 8/8 agree on systemd. They are NixOS-native and need no new supervisor code. The runner needs per-VM Nix evaluation. The Go supervisor's own problem is console and adoption coupling (gpt-6.1), which units remove. |
| Reconciler vs imperative operations | Imperative durable operations **plus observational reconciliation** | Unanimous amendment (codex, gpt-6.1, luna). Reconcile what *happened*; never perpetual `want=running`, which conflicts with the crash rule. |
| Heartbeat | **Required as observation; never stop authority** | Dissent upheld (gemini, muse, deepseek). Without it, fail-closed unknown becomes invisible stranding. The lease stays the sole stop authority. |
| Alive-unready timeout (gemini: 15 min → degraded) | The timeout escalates **visibility** (owner prompt, holder list), never destruction | Keeps thesis rule 1 while meeting the stranding concern. |
| Instrument first vs fix first | Receipts land first, alone; then disarm; then close | Dissent upheld (claude, glm). Otherwise closing the paths destroys the only chance to attribute the 09:25:48 caller. |
| polkit-scoped vmctl | Dropped from Phase 1 | claude and gpt-6.1: polkit does not sandbox a root controller. A non-root vmctl is a later, separate red step. |
| New intent store | None; extend corpusd `lifecycle_control` fates | Avoids dual authority. |
| Split `vmcore` binary | Not now | Units deliver restart immunity, and a second protocol is a burden for a solo owner. |
| Route CAS out of vmctl | No (doctrine) | Decouple adoption from it, and keep its calls off the locks (gemini). |
| Replace Firecracker; merge into proxy; event-sourced actuation | No | Unverified compatibility; a wider blast radius; a host actuator must not append semantic events. |

### 2.5 Expected deletions (estimate, to be measured)

- Legacy supervision and adoption, after drain: pid files, `/proc` scans, orphan cleanup, reap grace, OOM reconcile, reattach and demotion. About 1.2–1.5k lines.
- Pressure reclaim: 648 lines.
- Retention and pulse leave vmctl: about 1k lines.
- The package server and reverse proxy leave vmctl.
- The duplicate resume path, after caller migration.

Target: vmctl plus vmmanager under about 8k lines, with no file over about 600.

## 3. Confidence and biggest risk

- **Panel confidence:** medium to medium-high. It is high on the diagnosis and medium on the systemd and lease execution, which need a Node B spike.
- **Biggest risk, named by every panelist in some form:** a *partial rollout*. For example:
  - adopting alive-unready guests while health-driven recovery is still armed, which feeds them into a kill path;
  - fail-closed protection without bounded admission, which ends in host OOM;
  - removing `KillMode=process` before legacy children drain, which kills every running computer at once.

  The Phase 0 ordering and the separately verified drain step exist to prevent each of these.

## 4. Relation to Gate 2

Gate 2 reruns on QA computers are exposed to:
- every deploy (restart → reattach skip → boot over the guest);
- the 2-hour busy-protect expiry;
- the 2-minute no-row reap;
- browser and proxy escalation.

So Phase 0 comes before M11 rerun 12, or rerun 12 runs with no pushes during it. Phase 0 is the critical path for self-development's acceptance, not a detour.
