### Non-Blocking Findings

1. **Uppercase schemes in `openExternal` (`Intent` matching on Android)** — [AutoradioModule.kt:51,88](file:///Users/wiz/Dev/go-choir/.lane/trees/android-package/mobile/exact-package/android/AutoradioModule.kt#L51)
   - `route()` lowercases `scheme` when validating, so `"HTTPS://Example.org/x"` (tested in [SourceLinkTests.swift:8](file:///Users/wiz/Dev/go-choir/.lane/trees/android-package/mobile/AutoradioKit/Tests/AutoradioKitTests/SourceLinkTests.swift#L8)) or `"MAILTO:a@example.org"` is accepted, but `Uri.parse(...)` preserves the uppercase scheme in `Intent(Intent.ACTION_VIEW, uri)`. Because Android `IntentFilter` scheme matching is case-sensitive lowercase, `startActivity` will throw `ActivityNotFoundException` and `openExternal` will return `false` unless `.normalizeScheme()` is applied.

2. **`java.net.URI` RFC 2396 strictness on query/path characters** — [AutoradioModule.kt:33](file:///Users/wiz/Dev/go-choir/.lane/trees/android-package/mobile/exact-package/android/AutoradioModule.kt#L33)
   - `java.net.URI` rejects unencoded `[` `]` `|` `^` `{` `}` in query strings/paths (e.g., `https://example.com/?filter[tag]=news`) and leaves `parsed.host` null for hostnames containing `_`, whereas `Foundation.URL(string:)` on modern iOS/macOS accepts `[`/`]` in queries. On Android `shouldOverrideUrlLoading`, an in-page link/redirect with unencoded `[`/`]` in its query falls into `LinkRoute.refused` and is blocked on main-frame navigation.

3. **Updating `page` prop after `onRenderProcessGone` leaves `PageWebView` inert** — [AutoradioModule.kt:155-165](file:///Users/wiz/Dev/go-choir/.lane/trees/android-package/mobile/exact-package/android/AutoradioModule.kt#L155-L165)
   - `onRenderProcessGone` calls `destroyPage()` (`destroyed = true`). If the `web-page` node stays mounted and receives a new `page` prop without unmounting first (e.g., `BarWebLayer` updating `qv.webUrl` directly), `show()` returns early on `if (destroyed) return` without emitting `"failed"` or recreating the `WebView` (since `PageWebView` subclasses `WebView` rather than wrapping a replaceable `WebView` in a `FrameLayout`).

4. **Kotlin behavior is not executed by unit tests** — [android-package.test.ts:51-80](file:///Users/wiz/Dev/go-choir/.lane/trees/android-package/mobile/AutoradioLab/android-package.test.ts#L51-L80)
   - `P3` and `P4` are source-substring assertions only; they do not compile or run `AutoradioModule.kt` (e.g., under Robolectric/JUnit).

### Remaining Device-Proof Obligation

Before considering Android `web-page` / `readerOpenExternal` runtime behavior proved, verify on an Android device/emulator:
1. Opening a source link in `Reader` (`WebLayer`) and a bar URL (`BarWebLayer`) renders the `web-page` WebView transparently sized between status bar and lens, and transitions `webBusy` through `"loading"` -> `"done"` (and `"failed"` without a trailing `"done"` on an unreachable host).
2. Tapping an in-page `mailto:`/`tel:` link and triggering `readerOpenExternal` (`Open in Safari` / external button) launches the external app (`CATEGORY_BROWSABLE` for `http`/`https`) while `mailto:`/`tel:` passed via the `page` prop refuses in-app load with `"failed"`.
3. Backgrounding/resuming (`PAUSE`/`RESUME`/`STOP`) and closing `WebLayer` (`DESTROY` / `destroyView`) do not crash or leak/destroy an attached `WebView`.
