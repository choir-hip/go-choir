# The three Dolt stores: who owns what, where the bulk is, and what to cut (2026-10-28)

Status: design note, read-only investigation, nothing changed. Class of the note: green. Claims are [V] verified in code or docs (file:line named) or [H] hypothesis. Nothing was measured on a live host; every size is from an existing doc.

## 1. The stores

**Store 1, each computer's embedded Dolt.** [V] One workspace per VM on data.img, opened in-process (`docs/computer-ontology.md:157-160`). Two pools, each one connection, `db` and `readDB`; `engineMu` serialises `ogStore` and `ogReadStore` only (`docs/design/store-engine-concurrency-2026-10-21.md:19-29`, `internal/objectgraph/dolt_store.go:65-69,118-125`, `internal/store/store.go:985`).
- Writers: the projector (the only production writer of `og_objects`, outside the mutex), the runtime, Texture, the desk/selfdev code. Readers: the same process; /health, desks, GC.
- Tables: the tape projection `computer_event_index` (full `event_json`, `internal/store/computer_events.go:64`) plus heads; `choir_events` (run telemetry, `internal/store/event_table.go`); `og_objects`/`og_edges`; `run_memory_entries`; `og_key_index`; Texture and desktop tables; `texture_agent_mutations`.
- Size [V, 2026-10-19 census, after squash, `paper-disk-full-again-history-growth-2026-10-19.md:343`]: `computer_event_index` 1.36M rows, 3.84 GiB; `og_objects` 1.02M rows, 2.18 GiB; `run_memory_entries` 425k rows, 0.76 GiB; about 6.8 GiB raw. The 2026-10-28 compaction left 274 commits squashed to 2 and 26.5 GB (`paper-never-checkpointed-2026-10-27.md:644`) at 4.5M events. Scaling the 10-19 ratios, the tape index alone is about 12-13 GiB [H]. Dolt history, not data, was 40 of 48 GiB before squashing; a paper-wide 10 KB of retained history per event is recorded at `paper-dolt-journal-grows-1-6-gib-per-10-minutes-2026-10-22.md:510`.

**Store 2, the shared corpus (Store B).** [V] `corpus` database on `go-choir-corpus-dolt` (:13307, `nix/node-b.nix:1153`; MemoryMax 7G). Written only by corpusd, authenticated as the writing computer; read by corpusd for logged-out reads and every computer's shared reads (`docs/autopaper-sw-design-2026-10-09.md` "Storage that cannot repeat the 104 G problem"). Holds `og_*` (web_capture, published Textures and revisions, artifact manifests, retrieval kinds; `internal/objectgraph/registry.go:78,179-191`) and ignored projection tables `proj_capture_index/terms` (`internal/platform/capture_index.go:59,83`). Bodies are on host disk by hash, not in Dolt rows. Size is dominated by capture `og_objects` rows plus history; the 2026-10-09 store grew to 104 G the same way (2.4M items, 8.8M objects, commit per debounced batch; `docs/evidence/world-wire-store-b-inventory-2026-10-09.md`). I found no weekly squash for it in `nix/node-b.nix` [H: none exists].

**Store 3, the platform store (Store A).** [V] `platform` database on `go-choir-platform-dolt` (:13306). Tables: `computer_event_heads`, append receipts, lifecycle, checkpoints, route-projection certificates, `computer_projection_jobs/bases/epoch_roots/pins`, `computer_checkpoint_verdicts`, key escrow, owner acts, consensus (`internal/platform/computer_events.go:18-144`, `projection_jobs.go:20-82`, `store.go:71-210`). Writers: corpusd (head CAS, jobs), vmctl, checkpointd, via the 45 s debounced committer (`internal/doltbatch`). Size: 120,335 commits, 50.89 GiB (`store-a-weekly-squash-2026-10-20.md:350`), grown by history at about 1.6 GB per day (`:20-30`). `store.go:146,165` still declare `og_objects`/`og_edges` here; the ontology calls Store A's og tables pre-split leftovers (`computer-ontology.md:153-155`) [H: dead weight in the squash's live set].

## 2. Duplication

- **Captures: already not on the paper.** [V] `poll_source` writes `choir.web_capture` to Store B through corpusd (`internal/researchtools/poll_source.go:66-68`), settled 2026-10-11 (`autopaper-captures-built-per-computer-against-store-b-2026-10-11.md`). The registry's `Owner: OwnerCorpusd` agrees (`registry.go:78`). So captures are not the paper's bulk [H: a census of `og_objects` by kind on the paper is still missing; `data-has-more-than-one-home-2026-10-24.md:150` asks for it].
- **Source entities and refs.** [V] `choir.source_entity/ref` are `IdentityContentHash`, `OwnerVMStore`, Texture-written (`registry.go:76-77`). They cite captures; they could be adopted by id and version, but they are per-computer.
- **Stories.** [V] Published Texture revisions are copied into Store B on publish; the paper's own revisions remain in its `texture_revision` rows (`registry.go:98`). [H] A published revision is a duplicate of the paper's copy.
- **The tape projection is the largest duplicate.** [V] `computer_event_index.event_json` stores each event whole, while the event also exists as an immutable host artifact (`internal/platform/event_artifacts.go`; `computer-ontology.md:75`: embedded state "is never the sole durable event copy"). [H] About 12 GiB of the 26.5 GB is that copy, and it is content-addressed by `event_digest` and append-only.
- **Immutable vs authority.** [V] `IdentityContentHash` kinds include event, channel_message, inbox_delivery, run_memory_entry, texture_revision, content_item, source_entity/ref (`registry.go:76-101`). Authority state is `IdentityExternalKey`: agent, run, work_item, trajectory, run_acceptance, texture_document, settings. [H] Immutable kinds plus the tape index are most of the bulk; authority state is small. The owner also ruled that the paper "doesn't have unique data" (`paper-never-checkpointed-2026-10-27.md` owner decision S2).

## 3. Contention

- `engineMu` is taken by about 30 call sites in `internal/objectgraph/dolt_store.go` (Get/Put/List/Count paths, e.g. `:137,148,658,711,1058,1159`), `newest_headers.go:41-191` and the derived-keys validator (`derived_keys.go:601,641`). The projector and `db` users (events, run memory, selfdev) do not take it.
- /health does not use `engineMu`. [V] Its three reads go to the one write connection and give up in a budget; `store_stalled` carries the mutex state as a side field (`internal/agentcore/api.go:674-686,774-835`). So a GC or long write holding `db` stalls health; the mutex is only the second cause. Measured: online GC is 81% of the non-200 samples (`paper-remaining-store-stall-holders-2026-10-23.md:34-40`); on the mutex, reads are 89% of held time and `GetObject` is 10.7k calls per 122 s at 1.4 ms (`store-engine-concurrency:57-71`).
- **B2b (unimplemented, red).** [V] Keep `engineMu` for writes; cache immutable `IdentityContentHash` objects in `GetObject`; classify the 46 `ogReadStore` sites as snapshot-safe or authority; give snapshot-safe reads two connections without the mutex; raise `MaxConcurrent` last (`:113-146`). Two probes show reads see commits and several readers beside a writer are race-clean (`:85-111`). The paper has 2 vCPUs, so overlap is worth at most about 2x (`:67-71`).
- **Derived keys validation.** [V] `og_key_index` is "unvalidated at every open, never persisted as valid (an older binary would leave that lying)" and revalidated by a paged pass at up to 25% engine duty (`derived_keys.go:14-26,560-600`). [H] Persisting "validated through commit X" and checking `dolt_diff` from X to WORKING for `og_objects` would be rollback-safe, because a diff sees every writer, an older binary included. Two catches: the daily compaction squashes history to 2 commits, so X vanishes and a full pass is needed once a day (`paper-never-checkpointed:387`); and the marker row must be skipped by the replay and witness extractors like `og_key_index` itself (`derived_keys.go:34-36`). Use the table root hash at X as a cross-check.

## 4. Options, ranked by payoff over cost

1. **(d) Split immutable, append-only tables out of the authority store.** Move the tape projection and the content-hash kinds (events, messages, run memory, revisions) to a second database, with its own engine mutex and its own witness. Substrate: store open, projector routing, witness extractor, checkpoint base layout. Class: red, tier 2. Risks: cross-store atomicity (the tape stays authority, so the second store is a rebuildable projection; the `choir_events` stamp in `store/event_table.go` is the precedent for tape-stamped table routing); the guest restore path. Payoff: engine contention drops by the split share; the authority store shrinks to a few GB, so witness, clone and compaction cost fall in proportion (the paper's 2 h and 70 GiB clone growth: `paper-never-checkpointed:617-660`). The immutable half can be fetched from artifacts rather than stored, which is "adopt" in the strongest form [H].
2. **(a) Health off the engine.** Serve /health from a snapshot a watcher refreshes; keep `store_stalled` as a field. Substrate: `internal/agentcore/api.go`. Class: orange. Risk: hiding a real stall, since the updater reads `store_stalled` as a signal (`internal/updater/runtime.go:152`). Payoff: removes false unreachability and the GC-window 503s. It does not reduce capture or checkpoint cost.
3. **(c) B2b.** Cache first (immutable kinds), pool second. Class: red, tier 2. Payoff at most about 2x on reads. Shrinks capture only indirectly. Do the cache step alone first; it is cheap and independent.
4. **(e) Readers at a pinned committed root, one batched writer.** Substrate: store and projector. Class: red, tier 2. [H] Dolt table files are immutable, so a witness over a pinned root's per-table hashes (S3, `paper-never-checkpointed:117-120`) need not pause the guest or clone and compact it. Authority reads cannot use it, and the pinned root lags up to 100 events. Large payoff for checkpoint and witness, high build cost.
5. **(b) Incremental derived-keys validation.** Class: orange. Payoff: removes the post-boot validation duty; small once the daily compaction forces a full pass anyway.

## 5. Store A squash memory

The OOM: peak 10,737,422,336 bytes at MemoryMax 10G, 16.4G read, 12.3G written, 2m20s CPU (`store-a-weekly-squash-2026-10-20.md:349-353`).

- Phases in `internal/projectionbase/squash.go`: ref checks and counts (`:140-190`, a scan of `dolt_log` and `dolt_commit_ancestors` over 120k commits, small); `DOLT_RESET --soft` and `DOLT_COMMIT -A` (`:223-233`, a ref move and a commit of an unchanged root, which writes little); `DOLT_GC('--full', '--archive-level','0','--incremental-file-size', 256MiB)` (`:251`). Written bytes of 12.3G cannot come from the reset or commit. [H] The GC holds the peak.
- Why it exceeds the paper's 6.1G: that run was 7.5 GiB of live data at `GOMEMLIMIT=5GiB GOGC=50`. The 256 MiB flag bounds each output file, not the mark set. [H] GC memory scales with live data, not commit count. The run had already written 12.3G, so the live set is at least 13 GB, over 1.7x the paper's, and 6.1 x 1.7 is above 10G.
- The Go limit does not bound it: `cmd/platform-dolt-squash/main.go:41-47` sets only a soft 5 GiB `debug.SetMemoryLimit`, and the doc already notes cgo/mmap escape it (`:355-357`). The unit sets no `GOGC`.
- Bound it, in order: (1) measure on a reflink copy under `systemd-run -p MemoryMax=24G`, recording peak per phase, to settle the hypothesis (read-only to production); (2) shrink the live set before the GC by dropping Store A's dead pre-split `og_objects`/`og_edges` and other derived rows, then recount [H]; (3) set `GOGC=50` as in the paper's proven run and raise MemoryMax to what the stopped host affords (31 GB host, services down); (4) if live data exceeds the host, use the 2026-08-26 route: dump current state and import into a fresh repo, a streaming process with no GC mark set (Store B's 23 GB dump took 17 minutes). Also fix the unquoted `SQL_CHECK_CMD` (`nix/node-b.nix:2342`).

## 6. Recommendation

Do the census first (a read-only `og_objects`/table size breakdown on a reflink copy of the paper, the gap named at `data-has-more-than-one-home:150`), then build (d) as an extension of the `choir_events` stamping, starting with the tape index, since it is the largest, append-only, and duplicated by artifacts. Ship (a) now as the cheap symptom fix. Run squash step (1) before any further Store A attempt; no second blind run.

## Correction by FP0 (2026-10-28): option (a) conflicts with a settled decision

"Health answered off the engine" is not a cheap fix. `/health` reads the
store on purpose (internal/agentcore/api.go:673-700, decision F1 of
docs/problems/paper-unreachable-minutes-after-every-boot-2026-10-22.md): a
held write connection answers 503 `store_stalled` at once, never a 200. The
reads it waits on are authority reads. The effective release is what the
updater's identity probe checks. The live-capsule count is fail-closed and
feeds the restart refusals (S5). Serving them from memory would report
healthy exactly when those answers cannot be trusted. The 503 is an honest
signal of a held connection. The fix is at the substrate: the online GC's
hold, which is 81% of the non-200 samples, and the store split (d). Option
(a) is withdrawn from the ranking unless the owner reverses F1.
