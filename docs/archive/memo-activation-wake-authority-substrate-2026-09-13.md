## The pattern

Four distinct strands in the activation/lifecycle substrate share one cause:
**a lifecycle transition happens (state moves to a pending/terminal form) but
no durable wake or retry authority is minted for the continuation, so the
work strands until an unrelated sweep, a restart, or an owner action
notices.**

## What the four strands share structurally

1. **The continuation is private to one process.** The pending state lives in
   the reducer (durable), but the actor that may continue it (a run, a
   watcher, a detached fate commit) is process-local or run-local. When the
   actor dies — boot passivation, run completion, context cancellation — the
   reducer state stays pending with no owner.
2. **Recovery is bolted on after the fact.** Each repair added a sweep
   matching one signature (pending owner instructions, fresh-mint runs,
   frozen+proposal, …). The sweeps are correct but enumerate states instead
   of being generated by the state machine.
3. **The worker-facing surface can lie by omission.** The bound run terminalizes
   (`completed`) on a run-loop conclusion while the reducer fate is still
   pending, so a worker that reads run state infers "settled" — the run's
   terminal state is not evidence of the fate (observed on `9ec36ecb`; also
   the desk-prose-vs-reducer-state class recorded earlier).

## What a substrate-level fix looks like

Per pending lifecycle state that requires a continuation, the transition
itself mints a **durable wake/retry authority**: a recovery occurrence bound
to the new state, consumed by any later process (boot reconcile, Super
selection sweep, resume watchdog) through the same dispatch path fresh work
uses. Concretely:

- **Mint at transition.** `SetCoSuperCapsuleDisposition`, `BindCoSuperAssignment`,
  queue-owner-instruction, and drainer mint each arm a recovery occurrence
  (the pattern the fresh-mint fix already uses) — one mechanism, four
  call sites.
- **One consumer.** The boot reconcile + Super selection sweep consume
  recovery occurrences instead of each maintaining its own signature list.
- **Run-terminal ≠ fate-terminal.** The run projection must not report
  success while the reducer fate is pending; the worker-visible surface
  derives from the assignment record, not the run state.
- **The detached fate commit gets an idempotent resume**, not a retry loop
  inside one context: the revocation step itself must be re-enterable from
  the stored revoke intent (its effects are force-destroy + typed receipt;
  both idempotent by construction).

## Why this is not another incremental patch

The fourth fix would be `resumeStrandedFrozenAssignmentCommits` extended to
the `revoke_requested` signature. That works in-process but cannot rescue a
strand after a restart (the capsule is gone), and it leaves the intent-ladder
conflict (the stored revoke intent vs the report's freeze intent) for the
next transition to trip over. The class survives each local fix because the
continuation authority is minted nowhere and consumed everywhere ad hoc.
