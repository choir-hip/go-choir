# Choir roadmap to launch

Date: 2026-10-31. Status: **the owner's roadmap, stated by the owner on
2026-10-31; this is the canonical sequence.** It supersedes the sequencing in
`archive/reports/roadmap-sequencing-appdev-security-2026-10-14.md` and the
2026-09-22 mission stack. `ACTIVE.md` names the live station within it.

Owner, 2026-10-31: "that's my mental roadmap. And I don't want it to be mental
anymore. We should document this ... we should be clear and unequivocal."

The friends-and-family preview runs now, through every stage. Launch is the
end of the sequence, not the first time anyone sees Choir.

## The sequence

1. **The data system.** The fleet on the new data system, with state growth
   under control and no memory spikes (the lean system,
   `definitions/choir-lean-system-2026-10-30.md`).

2. **The Mac app with sync.** The owner's Mac follows its computer's tape,
   and the groundwork for the whole native layer is laid. Not all of it is
   built in this stage, but the essential groundwork is: the end-state design
   is `design/resource-fabric-2026-10-31.md`. That design covers workstations
   as sites in one resource fabric, the Mac leading, bursting across host and
   workstations, Choir in Choir, the native install as a general capability
   point (computer use, the File Provider, on-device voice and models, other
   native APIs), and an organization of workstations. Near-term builds back
   into it. Email sign-in (`design/email-sign-in-2026-10-31.md`) is part of
   this stage because it lets the Mac app be tested with no person.

3. **Perspective self-alignment (PSA), self-development, and the Autopaper
   product.**
   - Improve the Autopaper at the product level: images in articles; a much
     better op-ed section, personalized.
   - PSA for self-development and for the newspaper.
   - A learning system: the computer always makes precommitments and scores
     them as the evidence comes in (`precommitment-records.md`), and that
     record tunes the system: prompts and the REPL affordances change on it.
   - The desk seed goes (`problems/desk-runs-seeded-from-prior-run-2026-10-31.md`:
     "a no good pattern"). In its place a desk may get a small **calibration
     seed**, built from its history of precommitment records and their
     scores.
   - The old agent critical path fixes
     (`problems/old-agent-critical-path-2026-10-31.md`) come first in this
     stage.

4. **The voice layer and Autoradio.** Dictation, read aloud, and the full
   hands-free voice mode, which makes the computer an automatic radio. Then
   the product layer for Autoradio, which is the whole iPhone app. The Mike
   repository (`~/Dev/mike`) already holds on-device dictation, read aloud and
   a hands-free voice engine, built with this step in mind
   (`design/resource-fabric-2026-10-31.md` section 6). This stage completes
   the functional requirements for launch.

5. **The non-functional requirements: the four S's** (secure, scalable,
   stable self-development; `design/branching-tape-2026-10-31.md` section 9).
   More servers, zero-downtime deploys, and a better auth system (work on it
   is under way now, e.g. email sign-in).

6. **Agentic red teaming through self-development.** Use self-development to
   find out what it looks like when agents try to break out of their
   sandboxes, harden against what that finds, and define the security model.

7. **The economics model.** Which services Choir offers, at what prices,
   initially.

8. **Launch.**

## Rules that follow from the order

- Work on a later stage waits until the current stage is done, unless it is
  groundwork the current stage needs. Owner, 2026-10-31: "Anything which is
  about self-dev, autopaper, or psa, waits until after we get storage growth,
  memory spikes, and mac app/sync working well."
- Design looks to the end state even while the build follows the order.
  Owner, 2026-10-31: "design the system with the end in mind ... the design is
  going to then feed back into our next steps even before we get it working in
  full."
- Resources are used where they are: workstations run VMs, computer use, voice
  and local models when they have the memory, CPU and storage, and the server
  stays the place every device can reach and the burst capacity beyond one VM.
