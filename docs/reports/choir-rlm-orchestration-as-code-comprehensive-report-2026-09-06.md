## Introduction: The Imperative of Orchestration as Code

The overarching mission of Choir is the realization of the automatic computer: a persistent, self-governing computational substrate capable of supervised self-development. For an autonomous software system to safely inspect, modify, compile, test, and promote its own code, its internal agent harness must possess compositional integrity. In the earlier generations of autonomous agent architectures, execution was mediated through legacy JSON tool calling. Under that paradigm, every file read, directory search, command invocation, and state inspection required an explicit roundtrip across the network to a language model. The model was forced to act as an external program counter, repeatedly marshaling arguments, awaiting responses, and synthesizing next steps over fragile JSON schemas.

This traditional approach suffered from a fatal structural flaw: tool domain-specific languages are not closed under composition. When an agent needed to read fifty files to identify a shared dependency, or execute a compile-and-test loop with conditional branching, each step consumed tens of thousands of tokens of prompt context, incurred multiple seconds of network latency, and exposed the process to non-deterministic failure at every intermediate tool call. Most critically, because language model context windows are ephemeral, complex multi-step workflows suffered from cognitive decay as tool outputs accumulated in the prompt.

The Recursive Language Model architecture fundamentally replaces this paradigm with orchestration as code. The core doctrine is simple yet profound: code is closed under composition. Instead of equipping the model with dozens of ambient JSON tools for basic operating system tasks, the harness provides a single, persistent, stateful programming environment. The agent expresses its operational intent by writing native Go code executed directly inside an isolated guest capsule. Loops, conditionals, memory buffering, data transformations, and parallel inspections are handled natively at machine speed by the Go interpreter. The model only receives the concise final computation or targeted diagnostic report. By shifting execution from chat-based tool choreography to compiled and interpreted language runtime semantics, Choir transforms the agent from a passive caller of remote procedure calls into an active systems programmer.

## The Architectural Anatomy of the Four Planes

The realized target architecture cleanly disentangles the disparate concerns of computation, operating system interaction, inter-agent coordination, and durable state authority by partitioning the execution environment into four distinct planes.

The first plane is the Computation Plane, embodied by an in-memory, stateful Yaegi Go interpreter running within a dedicated guest session worker. Within a single activation, variables, helper functions, imported packages, and constructed data types persist across sequential cell evaluations in the interpreter heap. This allows an agent to inspect a repository structure in a first cell, define custom analysis routines in a second cell, and apply those routines across thousands of source files in subsequent cells without re-declaring types or re-parsing imports. To prevent state pollution from broken experiments, the computation plane is strictly fail-closed: any cell that encounters a compilation error or runtime panic poisons the interpreter session, requiring the activation to hydrate cleanly from durable storage.

The second plane is the Capsule-Effect Plane, which handles synchronous operating system syscalls. When an agent invokes file operations such as reading, writing, or listing directories, or when it executes operating system commands, those actions are not routed back to the host language model harness. Instead, they execute immediately within the dedicated microVM capsule assigned to that activation. Real file modifications occur directly within the capsule's writable overlay filesystem. This guarantees that file mutations are physically bound to the candidate workspace and completely invisible to other concurrent activations or the host operating system.

The third plane is the Intent Plane, which resolves the classic distributed systems deadlock problem that plagues multi-agent architectures. In legacy harnesses, when an agent attempts to send a message to a peer or spawn a subordinate worker, the call either blocks the executing process awaiting a response, or it triggers an out-of-band network effect while local execution is still uncertain. Choir resolves this through an in-memory intent tray. When an agent in a Go cell calls messaging, spawn, or completion functions, those calls return immediately with local receipt tokens and execute with zero network blocking. The resulting intent envelopes remain buffered in memory until the cell completes successfully with an exit code of zero. If the cell fails, panics, or times out, the entire tray is discarded without having emitted a single external side effect.

The fourth plane is the Durable Authority Plane, governed exclusively by the host-side supervisor and the Dolt relational version graph. Once a Go cell returns successfully, the host reduction engine extracts the staged intent tray, authoritatively commits the envelopes to durable logs, and delivers messages to resident recipient Go-channel mailboxes. It is here that host-signed execution receipts are minted and cryptographically bound to the capsule worktree. Crucially, the model's transient execution environment never acts as its own state authority; the database remembers, while Go delivers.

## The Engineering Journey: Substrate Before Symptom

The path from the initial design proposal to a verified staging deployment was defined by rigorous adherence to Choir doctrine: substrate before symptom, and problem documentation first. When autonomous runs encountered blockers on staging, the harness rejected the superficial temptation to patch language model prompts or add brittle prompt prohibitions. Instead, every failure was investigated to its architectural root, documented in formal problem receipts, reviewed across frontier model consensus panels, and repaired directly in the systems substrate.

The first major substrate failure involved a split-brain in actuator routing. While the host configuration intended to route execution through the new Go session interpreter, the guest microVM boots had no authoritative mechanism to determine whether they were operating under legacy tools or the new architecture. This ambiguity was permanently resolved by introducing a verified boot parameter channel, wiring the actuator mode directly into the Firecracker microVM kernel command line. This established a single, tamper-proof trust root: the guest kernel command line governs the broker dispatch, falling back safely to legacy tools only if the parameter is absent.

The second barrier emerged within guest operating system security boundaries. To guarantee that misbehaving or long-running worker processes could be cleanly reaped within five hundred milliseconds, the session worker was designed to isolate commands in separate process groups. However, upon deployment to staging, process group creation failed with permission denied errors. Investigation revealed that the microVM's strict default seccomp filter blocked the setpgid system call. Rather than disabling security isolation or abandoning process group cleanup, the seccomp manifest was surgically updated to authorize setpgid, restoring guaranteed process-group termination without compromising container security.

A third and particularly elusive substrate obstacle arose within Linux Landlock security policies. During initial live tests, the agent was able to read files and modify existing inodes within the capsule overlay, but any attempt to create a new file resulted in access denied errors. Forensic inspection revealed that while the Landlock filesystem rules correctly granted directory write permissions, Linux Landlock V5 requires an explicit regular file creation permission to permit overlay filesystem copy-up of newly created files. Adding the regular file creation flag unblocked in-capsule file generation while maintaining strict sandbox isolation against unauthorized host paths.

Subsequent substrate enhancements addressed the cognitive ergonomics of code execution. Autonomous language models frequently wrap executable code in markdown code fences. Rather than penalizing models or prompting against this natural tendency, the Yaegi kernel and broker boundaries were enhanced with clean source normalization, transparently stripping markdown formatting prior to compilation. Simultaneously, the command execution engine in the capsule broker was rewritten to replace shell-wrapped execution with direct-argv execution under a strictly controlled environment allowlist, eliminating shell injection risks and environment secret leakage. Finally, a severe deadlock in the Super agent's global first-in, first-out message processing queue was eliminated by implementing exact control binding, guaranteeing that targeted activation turns bind their intended work items rather than stalling behind unrelated historical packets.

## Frontier Model Agentic Consensus

Throughout this transformation, architectural proposals, substrate patches, and operational changes were continuously subjected to multi-model agentic consensus panels. Drawing on eight independent frontier models—Claude Opus, GPT-5.6 Sol, GPT-5.6 Terra, GPT-5.6 Luna, Gemini 3.8 Flash, Grok 4.6 High, Cursor Agent, and OpenCode—the consensus process served as an adversarial assurance gate.

The consensus panels established several non-negotiable architectural invariants. They unanimously ratified the spatial isolation invariant, affirming that each activation must operate within its own dedicated, disposable capsule, sharing only immutable, content-addressed lower filesystem layers. They adjudicated the boundaries between memory and storage, affirming that in-memory Go heaps are the appropriate domain for conversational and intermediate computational context, whereas Dolt is the sole domain for durable work items, events, and trajectory evidence.

Furthermore, the consensus panels guided the evolution of the prompt architecture. Early cutover attempts relied on dense catalogs of negative prohibitions, instructing models on what they were forbidden from doing. The consensus review demonstrated that models perform substantially better when provided with an actionable, affirmative mental model. Consequently, the prompts were restructured to teach the metaphor of a stateful Go notebook kernel, complete with three-cell worked traces demonstrating how to inspect a workspace, execute modifications, and stage terminal completion receipts.

## Forensic Analysis of the Discovered Heresy

Despite the triumphant execution of the in-capsule Go program, the assignment did not achieve a clean terminal pass disposition in the host ledger. Instead, when the agent attempted to submit its final assignment result, the runtime returned a lifecycle command digest conflict error. In accordance with Choir doctrine, this anomaly was not swept aside as a transient glitch, but treated as a primary systems discovery.

A fourth agentic consensus panel was immediately convened to review the execution telemetry, and seven frontier models completed exhaustive forensic analyses. Together with source inspection, the exact mechanics of the failure were laid bare, tracing to a subtle defect spanning the tool loop control structure and the state machine's identity derivation.

The first component of the defect lives in the tool loop engine. When an agent executes tools, the harness contains an early-exit optimization designed to terminate the loop as soon as a detached terminal reporting tool succeeds. However, the logic specifically required that the turn contain exactly one tool call. In the observed run, the language model issued two tool calls concurrently within the same turn: the Go evaluation tool and the record assignment result tool. Because the turn contained two calls rather than one, the early-exit condition was skipped, and the tool loop proceeded to execute an unnecessary subsequent iteration.

The second component of the defect lives in the assignment fate state machine. When the model was prompted for the next iteration, it attempted to call the record assignment result tool a second time. The host store assigns a deterministic command identifier to capsule freeze operations, keyed strictly on the assignment identifier, the attempt number, and the requested disposition. However, the command digest for that operation incorporated a terminal fingerprint that was computed from a report identifier, which in turn hashed the transient, provider-specific tool call identifier.

Because the tool call identifier on the second turn was distinct from the tool call identifier on the first turn, the computed command digest changed, even though the command identifier remained identical. When the store attempted to process the second call, its idempotency replay check detected that a command with that identifier had already been recorded with a different cryptographic digest. The store correctly and uncompromisingly rejected the operation as a lifecycle command digest conflict.

This finding revealed a profound single-authority violation: the command identifier asserted that freeze operations are unique per assignment attempt, yet the command digest allowed that identity to be fragmented by transient network transport tokens. The consensus panel unanimously affirmed that the fix must operate at the substrate level: terminal report identifiers must be derived strictly from durable assignment coordinates and semantic payload content, completely removing transient transport tokens from the identity hash, while the tool loop must be updated to terminate whenever any terminal reporting tool succeeds within a batch.

## Next Realism Horizons: The Road to Self-Development

The live execution on epoch 888 represents a watershed milestone: the mechanics of orchestration as code, guest capsule confinement, direct-argv execution, and kernel-verified actuator routing are now proven operational realities on staging hardware. However, Choir doctrine demands absolute truth in reporting: proof of execution is not proof of completion.

Because the assignment was unable to close its own fate in the host database, the Definition 2 cutover cannot be declared fully complete. Run state is not assignment disposition. The current mission status is therefore marked as an accepted execution proof, with final run acceptance explicitly withheld until the two-layer settlement repair is implemented and verified.

The engineering sequence moving forward is clear and disciplined. The immediate next action is not the premature expansion of scope, but the landing of the surgical idempotency repair and the re-execution of the sealed proof until clean freeze, terminal pass, and capsule revocation receipts are committed to the Dolt ledger.

Once terminal settlement idempotency is established, the platform will advance along its defined realism trajectory. The first subsequent realism axis will exercise multi-cell notebook continuity, proving that variables, data structures, and compiled routines persist across sequential cells without re-declaration. The second axis will test spatial isolation under concurrent load, running multiple guest capsules simultaneously across distinct agent desks to verify namespace non-interference. The third axis will activate role-bounded subagent spawning and coalesced mailbox wakes. Only after these substrate layers demonstrate unwavering mathematical and operational integrity will write effects be enabled, unlocking the ultimate horizon of autonomous, supervised self-development.

The transition from brittle JSON tool calling to native Go orchestration marks the end of prompt choreography and the beginning of genuine systems engineering for autonomous computers. By demanding that code remain closed under composition, that execution remain bound to isolated guest capsules, and that state authority reside immutably in the relational graph, Choir secures the architectural foundation required for an automatic computer that can safely, verifiably, and indefinitely build itself.
