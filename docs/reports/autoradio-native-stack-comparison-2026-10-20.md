# Autoradio native stack: four options compared (decision report, 2026-10-20)

Status: decision report for the owner. Mutation class: green (docs only). It answers the owner's request in owner notes section 28: "consider using Wails V3 (wrapping our svelte...). I don't really think that's a good idea, but I just want to compare everything — from that to capacitor to UIkit plus Swift as needed to pure Swift." It refines section 6 of `texture-media-and-autoradio-design-2026-10-20.md`.

Facts about Wails, Capacitor, Apple and Android were checked on 2026-10-20. Sources are listed at the end.

## Summary

The current recommendation holds, with one refinement.

Build Autoradio as a native Swift app on iOS. Keep the shell, the audio engine, the lock screen, CarPlay, push, Face ID and passkeys native. Render Texture documents natively too, because the renderer is small. Use a web view only for the one thing that is a web page anyway, which is the YouTube embed.

The refinement is that "UIKit core" should be read narrowly. UIKit is needed for the player, the embed list and, later, the text editor. Version one has no block editing on the phone, so the reader and the settings screens may be SwiftUI where that is cheaper. That moves option three a little toward option four, and it is fine.

Wails v3 is not a good idea for this app. The owner's suspicion is confirmed. Wails v3 is still a beta. Its mobile support is labeled experimental. Its source has no code for background audio sessions, the lock screen, CarPlay or remote push.

Capacitor is the only wrapper worth a serious look. It fails on a different point. The audio layer has to be native anyway, so the wrapper would carry only the reader, and the reader is the cheap part to write natively.

The fact that most confirmed this: a field report from another Capacitor project found that web-view audio was paused once the page was hidden, and the page was suspended after about 26 seconds. The audio layer is a chain of timed segments, which is exactly the shape that breaks.

## What Autoradio must do

From the design document, Autoradio does these things.

It plays long-form background audio from the Texture audio layer. That is a timeline of segments, each tied to a block id. It needs an audio session, Now Playing, lock-screen controls and interruption handling. CarPlay comes later.

It reads Texture documents with embeds. These are images, video including YouTube, podcast episodes and capsule evidence screenshots and video.

It takes text and voice into the prompt bar to drive the autoputer.

It carries owner acts, which are approve, reject and roll back, with the evidence visible and Face ID as a step-up.

It works offline from a cache, and it receives push notifications.

The owner ruled on 2026-10-14 that the web desktop is not the phone app, and that Svelte may be used only in limited ways.

## Option 1: Wails v3 wrapping the Svelte frontend

**What it is.** Wails v3 compiles a Go program and a web frontend into one app. On a phone it puts the frontend in a system web view and compiles the Go code into the same binary, called in process.

**Where it stands today.** The latest release is v3.0.0-beta.33, published on 2026-10-19, and it is marked a prerelease. The project's roadmap says "Current Status: Beta". Its beta compatibility promise covers desktop only, and it says "Android and iOS support is experimental and does not block the desktop Beta." The iOS guide opens with "iOS support is experimental and may change in future releases." So the answer to the owner's question is: iOS and Android exist in v3, in source and documentation, but they are experimental and outside the stability promise. The v3 line is not final.

**What it gives.** Service bindings from JavaScript to Go, events, message dialogs, a file open dialog, clipboard, haptics, biometrics, local notifications, secure storage and text-to-speech appear in its kitchen-sink example. It can template `UIBackgroundModes` in the Info.plist. The iOS minimum is 15.

**What it lacks.** I searched the v3 application package and the mobile example on master. They contain no AVAudioSession, no Now Playing, no remote command center, no CarPlay and no remote push registration. The notifications are local. Only the first window is shown. So every item that makes Autoradio valuable would be hand-written native code outside Wails, inside a project generated by Wails. A bug filed on 2026-10-16 shows the mobile builds are still being repaired. A server build tag did not compile for iOS or Android until the fix on that day.

**What "Go in process" would buy.** Very little. The Go code in this repo runs on the computer, not on the phone. The phone talks to the computer over its API, and Swift can do the little client work that remains. Also, passkeys are bound to the choir.news domain through associated domains, and a custom-scheme page cannot present that domain (my inference, untested; it applies to Capacitor too).

**The risk that would kill it.** Its mobile layer is young and experimental. The audio and lock-screen work, which is most of the app, is outside what it offers. Capacitor offers more of the same idea on firmer ground. I rank it below Capacitor and below both native options. The owner's suspicion is right.

## Option 2: Capacitor wrapping the Svelte frontend

**What it is.** Capacitor puts a web app in a system web view and offers a plugin bridge to native code. The current stable release is 8.5.3, published on 2026-10-07. Version 9.0.0-alpha.8 is out as a prerelease. Version 8 uses Swift Package Manager for new iOS projects and needs Xcode 26 or later.

**What it gives.** It is the fastest path to a first build on both iOS and Android. It is mature, with a large plugin set. A push plugin exists for APNs and Firebase. It does not support silent background pushes. The configuration option that loads a remote URL is labeled "not intended for use in production", so the app must ship a bundled frontend.

**Audio.** The reliable route is a native audio plugin, not the web audio element. Capawesome's audio player has registered the session natively, with the remote command center on iOS, since version 8.4.0. Cap-go's native audio plugin uses the Now Playing info center and the remote command center. In both cases the audio engine is native code inside the wrapper. The web Media Session API is not a substitute. The Android WebView does not support it, according to the plugin author.

**Field evidence on the segment timeline.** A Capacitor project, foray, ran a spike on whether web-view audio survives backgrounding. In September 2026 its founder recorded on an iPhone that audio paused when the page was hidden, and the page was suspended after about 26 seconds. The founder then chose a fully native engine. The same spike warned that a timer-driven segment chain can keep playing audio while its out-points never fire. This is one project's report, not a controlled study, but it matches our design: a timeline of segments.

**CarPlay.** A third-party Capacitor CarPlay plugin offers simple list templates and says CarPlay does not render the web view. Apple states that only navigation apps get a window in CarPlay. Everything else uses templates through the scene delegate. So CarPlay is native whatever the shell is.

**What it reuses.** The Texture editor is a 2,654-line `contenteditable` surface, and the prompt bar is 632 lines. The reader code and citation popovers are written for a desktop window and the desktop auth flow. Reusing them carries a desktop's assumptions onto a phone, which the owner has ruled against.

**App Review.** Guideline 4.2 says an app "should include features, content, and UI that elevate it beyond a repackaged website." Guideline 2.5.2 forbids downloading or executing code that "introduces or changes features or functionality of the app." A Capacitor app that bundles its frontend and adds native audio, CarPlay, push and Face ID clears 4.2 comfortably, because the native features are the app. But then the native part is most of the app and the web part is the reader. Live-update services that replace the bundle sit close to the 2.5.2 line. I would not use them.

**Android.** This is Capacitor's real advantage. One Svelte reader serves both platforms. But the audio and Auto work are native Kotlin plugins, using the platform's Media3 session service, which Android requires for background playback. The Android WebView lacks the Media Session API, as noted above.

**The risk that would kill it.** The valuable parts are native anyway, so the wrapper saves only the reader, and the reader is a switch over about a dozen block kinds. The cost is a bridge that must carry audio position into the web view for highlighting, and push, passkeys and offline into native code. That is more total code than a native reader.

## Option 3: UIKit and Swift where needed (the current recommendation)

**What it is.** A native Swift app. The shell, the audio engine, the lock screen and CarPlay are native. The Texture reader is native, built from the closed `choir.texture_doc` schema. A web view appears only where the content is a web page, which is the YouTube embed. The plan in `autoradio-mobile-app-plan-2026-10-14.md` already sets this out.

**What it gives.** Apple's own audio recipe, directly. Apple says an app needs the `playback` audio session category, the Audio, AirPlay and Picture in Picture background mode, and an activated session to keep playing when the user switches apps or locks the device. Now Playing and remote commands are native frameworks. CarPlay audio is a scene with templates and needs an entitlement that Apple grants by approval. App Intents, Live Activities, widgets, APNs and passkeys through associated domains are all first-class here. Accessibility for a reading and listening app is the system's own: VoiceOver reads native text and controls without a layer in between.

**What it costs.** Two clients in the long run. Swift builds are slow, and the plan records the owner's complaint about this as a true one. The Mac is often under load, so a CI budget for build time matters. Agents write Swift well and can verify it with the simulator and XCUITest, though not as cheaply as Playwright on Linux.

**Reuse.** Not code. Three shared contracts carry the reuse. The first is the closed document schema. The second is the audio timeline format, which is data. The third is a set of golden documents that every renderer and every player must handle with the same block order and timings. This is the plan from section 6 and it stands.

**Android.** Kotlin and Compose, later. The same three contracts apply. Android's background audio uses Media3's `MediaSessionService` with a `mediaPlayback` foreground service, which exposes the player to the system, Google Assistant and Android Auto without the app's UI. The work is parallel, not shared.

**The risk that would kill it.** Android demand arriving before the iOS audio experience is proven. Then two native clients would be too early. A narrower fix is a reader-only Capacitor build as a stopgap, which the design document already names.

## Option 4: Pure Swift, SwiftUI first

**What it is.** The same native app, with SwiftUI as the main framework and UIKit only when SwiftUI cannot do the job, and no web views at all.

**What it gives.** The least code for lists, settings, sheets and approval screens. Version one has no phone-side block editing, so most of it is lists, cards and controls.

**What it costs.** The 2026-10-14 plan chose UIKit because SwiftUI is less predictable for large lists and text editing, and the Texture editor needs TextKit 2 through a UIKit bridge. That reason is weak for version one and strong once phone editing arrives. Dropping all web views also costs something. The YouTube player is a web embed, so it would need a web view in the end. A no-web-view rule would be broken on the first day, or the YouTube embed would become a link that leaves the app.

**Android.** Same as option 3. Compose is close to SwiftUI.

**The risk that would kill it.** Pain at the edges. Embed lists with video, a highlighted reading position and a live audio scrubber all push on SwiftUI's weakest points, and the escape hatch to UIKit is exactly option 3.

## How they compare

On audio, options 3 and 4 do it directly. Option 2 does it only through native plugins, and option 1 would need them written by hand. A field report shows web-view audio does not survive the lock screen.

On CarPlay, push and passkeys, the verdict is the same. These are native in every option. The wrappers add a bridge in front of them.

On the prompt bar and owner acts, native is better, because Face ID step-up and the approval sheet are system surfaces.

On App Review, native has no 4.2 exposure. The wrappers have some, which the native features reduce. Wails adds the risk of a pre-release toolchain.

On accessibility, native gets VoiceOver for free. A web view can be accessible, but custom controls need ARIA care.

On team reality, agents write Swift well, and it is checkable on a simulator. The wrappers add JavaScript, Swift and Kotlin together, which is the most surface for agents to keep consistent. Every iOS build, whatever the shell, still needs Xcode on a Mac, so wrappers do not relieve a loaded Mac. They add a build step.

On long-term cost, the wrappers are cheaper in year one and costlier after, because the native parts do not shrink. Native costs two clients but each is simple.

## Recommendation

Hold the decision: Swift on iOS, with native audio, shell and reader. Refine it in three ways.

First, treat UIKit as required where control matters, which is the player, the embed collection and later the editor. Allow SwiftUI for the shell, settings and approval sheets where it is cheaper. The plan's SwiftUI-last stance was driven by the editor. The editor is not in version one.

Second, allow one web view: the YouTube embed. Keep it sandboxed, and keep the app's own content native. This matches the owner's "Svelte may be used in limited ways", and it needs no Svelte at all.

Third, keep the reuse in the contracts, not the code. The schema, the audio timeline and the golden documents are shared across web, iOS and Android. Add the golden-document test to the web renderer's tests first, so that the Swift one has something to match.

I also weighed the two hybrids. Native audio with a web-view reader reusing the Svelte renderer pays for a bridge, double offline caching and a desktop-shaped renderer, to avoid writing a switch over a dozen block kinds. The reverse, a web shell with native audio, is Capacitor, with more App Review exposure. Neither beats native.

**What would change this.**

- If Android users matter before the iOS audio experience is proven, ship a Capacitor build of the reader alone, with no editor, as a stopgap. Revisit at the plan's M5.
- If the agents' Swift build times make the loop unworkable on the loaded Mac, move more of the shell to SwiftUI and keep the build times in CI budgets. Do not move to a wrapper for this reason, because the wrapper still needs Xcode.
- If Wails v3 ships a stable release and a first-party audio session, Now Playing and push layer, look again. It would still be a web view in a shell, so the other objections stay.
