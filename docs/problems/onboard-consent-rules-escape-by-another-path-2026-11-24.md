# onboard-consent: each rule held on the path that was fixed and escaped by another (2026-11-24)

**Problem.** Three review rounds on the phone app's first run found the same defect in new places. Round 1 fixed "a download needs a press" on the first-run button and the search model escaped through a shared flag. Round 2 fixed "readiness is written after the check" in setup and the voice cards (`VoiceSampler`) still wrote it at fetch. Round 3 found a retry, a resume and a Wi-Fi-to-cellular change spending mobile data under a Wi-Fi-only agreement, the voice cards fetching outside every consent group, and the learn page's microphone lease surviving any exit but its own two buttons.

**Evidence.** The reviews (`seat2`, `seat2-r2`, `seat2-r3`); each finding names the second path. The rules are enforced at call sites (a check before a button's work), and there are many call sites: setup, Settings > Downloads, the voice cards, retry, resume, the search pass, the voice-print fetch, the libraries' own downloads. A rule enforced at N call sites has N chances to be missed; every fix added the (N+1)th check.

**Belief (structural assessment, contract rule 7).** The fault is where each rule lives, not any one check. A rule that every path must obey has to live in the one function every path goes through, and the other paths have to be deleted so there is no path to forget:
1. **One download door** (`DownloadDoor`): the only way a model file reaches the phone. It takes the consent record (pushed from Exact's `consent.json`) and refuses a model whose group has no agreement; the transport it hands out is a URLSession configured with `allowsCellularAccess`, `allowsExpensiveNetworkAccess` and `allowsConstrainedNetworkAccess` equal to "the person agreed to mobile data", so a path change mid-download, a retry and a resume cannot spend mobile data. `ModelStore`, the voice-print fetch and the model provider all call it; a test drives a fetch through each former path with no consent and sees zero requests.
2. **One readiness writer** (`ReadinessVerifier`): the engine, the page and the voice cards only READ readiness (`VoiceReadiness` has `isReady` and nothing else); the one writer runs the check and marks only on a pass.
3. **The microphone lease is bound to the page's lifetime**: released by the page's presence (`learnOpen` false: any exit, not the page's buttons), by the app going to the background and by sign-out.
4. **Every voice-profile write carries the account generation captured when the operation began** (the turn, not the write).
5. **A credit for every licence that asks for one comes from the model list**: a test fails when a list entry whose licence is a CC licence has none.

**Round 4 (what a door being a convention cost).** A release gated by a running step (so a door that could be skipped), a library that could fetch whenever it was initialised, and a readiness that was an id set outliving its files were each a door that was a convention. Now: releases are not gated; the libraries' registry is closed except inside the one window; readiness is derived from the files and the pin.

**Remaining error.** The FluidAudio models are not pinned by file digest, and Silero, Kokoro, Pocket and Phonon cannot load without being able to fetch (no local-only entry point): they rely on the closed registry, which a phone must prove (they speak and listen after a relaunch with it closed). A transfer cut by a path change is cut by Task cancellation: a phone must show the bytes after Wi-Fi to cellular.

## Round 9: the deletion rule was single and scoped by the wrong thing (CLAUDE.md rule 7, ninth round on one subsystem)

**Problem.** Rounds 5 to 9 on the library models' files each fixed a rule and the next review found it deleting or keeping the wrong files by another route. Round 9: the one deletion rule (`ModelDeletion.reconcile`) compared a file set with the manifest of "whichever version sealed it", so after a `libraryPin` bump a complete new download was judged "damaged" against the old version's baseline and deleted (F1), and old-version files that still matched their old baseline were kept for ever with no way to remove them (F2). Around it: a first download whose warm load threw was deleted as a half pack (F3), a hung cold load wedged the one slot for the life of the process (F4), a refusal cleared a working voice's readiness (F5), and the setup ladder's own deletion path contradicted the "one function" claim (F6).

**Evidence.** The seat-2 reviews of rounds 5 to 9; `ModelPins.proof` (no pin check), `purge` (baseline left behind), `ModelFetch.guarded` (demotes before the door), `exclusive` (no cap), `LiveConfigBackend.delete` (a second deleter).

**Structural assessment.** Three rounds in a row the patch was "guard this comparison". The comparison itself is the fault: a manifest, a baseline and a pin record describe ONE version of ONE model's files, and nothing may compare across versions. So: (1) every record (manifest, baseline) is named by its pin and `proof` reads only the current pin's, so a different pin is "unknown", never "damaged"; (2) a fetch that the person asked for, under a pin whose files came from another pin, starts clean (the old version's folders and records are removed before it writes; FluidAudio chooses its own folders, so a pin-named folder with the old one kept until the new one seals is not possible without changing every library loader; this is the closest the libraries allow); (3) the person gets a Remove on every downloaded model that is not in use, so no state needs a reinstall to leave; (4) "the fetch did not finish" is evidence (the door killed it, or the error is a transport one), not "the body threw"; (5) no wait is unbounded: a body that never returns releases the slot after a hard cap while that model stays refused; (6) a fetch demotes inside the door, after admission.

**Remaining error.** The library's files are not in a pin-named folder, so for a moment during a re-fetch under a new pin there is no old version to fall back on (the old files are removed before the new ones are written). The "finished" evidence is a classification of the error (a transport error or a door kill means unfinished; any other error means the download finished and the load failed): a library that wraps a network failure in its own error type is read as a finished download and its half pack is kept, which the person clears with Remove. The manifest records every file in the library's folders, including any the library writes lazily during the first load: a rewrite of such a file later reads as "changed". Phone check (decides the build): seal a voice, use it, relaunch, force a failed load: the files must be kept and the card must say intact; then bump the pin and download: it must end ready.

**Round 10 residuals (named, not fixed).** (a) While a cold load is stuck its slot is released at twice the deadline (1200 s) but a fetch waits only five minutes for the slot, so for up to 20 minutes other models' fetches fail with a timeout (the stuck model's own windows and checks are refused at once); and after the cap another model's window can open while the stuck body still runs, so the stuck library can observe an open registry (the registry is process-global). (b) The setup configurator's rejected-configuration path (`LiveConfigBackend.delete`) still removes folders and readiness directly and leaves records; it is a second deleter, documented in `docs/changes.md`. (c) Phonon has no option and so no Remove. (d) A rewritten sealed file reads as a change at a failed check (the phone check above decides).

**Phone checks added (round 11).** (e) Kill the app (swipe away, or run low on memory) in the middle of a library voice's download, relaunch and tap the voice again: the card must clean the partial folder and download in full, and end ready. (f) Drop the network in the middle of Pocket's download so that the library gives its own (wrapped) error: the failed card must offer Remove on Settings > Downloads even though the voice is the one the person tapped, and a re-download after Remove must end ready.
