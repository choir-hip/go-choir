# Why starting b@c needed stopping d@e: memory and density on Node B

Read-only investigation, origin/main 99c4d9a9a (fetched 2026-10-26). Nothing run on Node B; no SSH. Evidence labels: **PROVEN** (code at the cited line, or a dated receipt), **HYPOTHESIS** (needs a live read named in the text).

## 0. The short answer

The system already has the pieces the owner remembers (snapshot hibernate with 0.1-0.4 s wake, free page reporting, sustained-signal reclaim, measured admission). What it lacks is the **coupling** between them:

1. **Admission only refuses; it never makes room.** `admitHostMemoryWith` (internal/vmctl/host_admission.go:370-450) compares one MemAvailable sample against `floor + headroom + reserved + need` and returns a `host_memory_pressure` refusal (503, Retry-After 60). Nothing in the refusal path hibernates anything. `docs/learn/04-computer-lifecycle.md` section 5.3 item 3 says so in words ("Admission and reclaim were not coupled: a refused start did not ask reclaim to make room"); section 5.4 lists "couple admission to reclaim" as an option; it was never built. This is the fourth recorded recurrence: 10-13 (new-owner-waits-while-qa-computers-hold-node-b-memory), 10-22 03:16 and 05:25 (ledger lines 56, 96), 10-26 03:1x (ledger line 1488), today.
2. **The idle computer was never going to be hibernated by policy.** Reclaim fires only when MemAvailable is under the floor (4779 MiB) AND memory PSI avg60 > threshold for 4 samples (pressure_reclaim.go:420-427). Admission refuses at 13.2 GiB available. Between 4.8 GiB and 13.6 GiB, starts are refused and nothing is reclaimed. A "primary" computer (d@e and b@c are neither paid, platform, nor in the ephemeral email domains) is additionally exempt from the 30-minute idle sweep while the host is not under reclaim pressure (warmness_policy.go:231, `VMCTL_PRIMARY_KEEPALIVE_MODE=under-capacity`, nix/node-b.nix:1826).
3. **The start's "need" is the last run's peak RSS, not what a snapshot wake takes.** b@c's 7847 MiB is its measured peak from its previous run, clamped to the 8192 MiB guest size. A snapshot wake of a computer lands at roughly 0.3-1.3 GiB resident (s3 evidence: 364 MiB after wake; vm-density-limits: 0.13 GiB private floor). The admission check charged b@c about 6.5 GiB it would not use for minutes, if ever.

The shortfall was small: required 4779 + 1024 + 0 + 7847 = 13650 MiB; available 13202 MiB; short by 448 MiB.

## 2. The admission rule that refused b@c

PROVEN, from code.

- **Where:** `admitHostMemoryWith`, internal/vmctl/host_admission.go:370. Message built at :448. Called from `startExistingVM` (ownership.go:1580), `rescueBoot` (ownership.go ~3874) and the locked variant (ownership.go ~2331). The error maps to HTTP 503 and `transientStartRefusal` (ownership.go:3950); `hostMemoryRetryAfterSeconds = 60` (host_capacity.go:25).
- **Rule:** `required = floor + headroom + reserved + need` (host_admission.go:418). Admit when `MemAvailable >= required`. A missing sample admits; protected classes (premium_always_on, critical_protected, public_platform; host_capacity.go:71) always admit but still reserve.
- **floor = 4779 MiB:** `memoryFloorBytes` (pressure_reclaim.go:250) = max(absolute, percent of MemTotal). Config: `VMCTL_PRESSURE_MIN_MEMORY_AVAILABLE_MIB=4096`, `_PERCENT=15` (node-b.nix:1832-1833). 15% of a 31.1 GiB MemTotal = 4779 MiB, which beats 4096. (Arithmetic from the refusal text; MemTotal itself not read today.)
- **headroom = 1024 MiB:** `DefaultHostAdmissionConfig` HeadroomBytes 1<<30 (host_admission.go:~70); a shared burst pool.
- **need = 7847 MiB "(measured)":** `estimateNeedWith` (host_admission.go:337): if the ownership has `MemoryPeakRSSBytes > 0`, need is that value (source "measured"), floored at 1 GiB and **clamped to the guest size** (8192 MiB for any non-platform computer, `machineShapeForOwnership`, ownership.go:1323; `VM_INTERACTIVE_MEM_MIB=8192`, node-b.nix:1648). Unmeasured computers get 2 GiB (host_admission.go:69). The peak is the maximum VmRSS of the Firecracker process(es) observed by `sampleVMMemory` (host_admission.go:508, reading `/proc/<pid>/status` VmRSS via vmmanager/process_control.go:127) during that computer's last run, and it persists on the ownership after the VM stops.
- **Does buff/cache count?** MemAvailable is the kernel's own estimate, which already includes the reclaimable part of page cache and reclaimable slab (the 13.1 GiB figure is that estimate; the 13.4 GiB buff/cache is not additional). The code reads MemAvailable only (`readMemInfo`, pressure_reclaim.go ~440). It does not look at what is inside it. HYPOTHESIS: some of the 13.4 GiB is not reclaimable (shmem, mapped snapshot files, btrfs inode slab under active use); the kernel's estimate is deliberately conservative.
- **Reserved:** 0 here. Reservations only cover starts admitted in the last 5 minutes (Settle) and in flight.
- **Does admission hibernate idle VMs first?** No. Grep of the whole tree finds `RecoveryRefusalHostMemoryPressure` constructed only in host_admission.go:447 and :492. The only hibernating paths are (a) the idle sweep (ownership.go:1228, `StopIdleVMs`) and (b) the pressure monitor (`reclaimSustained`, pressure_sustained.go:196). Both run on their own timers, not on a refusal.
- **Why d@e was still resident (PROVEN in code, class is HYPOTHESIS):**
  - Class: `warmnessClassForOwnership` (warmness_policy.go:115) returns `primary` unless the user is in computer-tiers.json (only the owner's paid account and the paper are listed; no `test_computers`), or is an ephemeral account (email domain `example.com`/`example.test` or id prefix `diagnostic-`/`sourcemaxx-proof-`, node-b.nix:1880-1881). `d@e` and `b@c` fit neither, so they should be `primary`. To confirm without SSH: vmctl health `warmness.by_class` and `idle_eligible_by_class` (warmness_policy.go `warmnessSummary`).
  - Keepalive: with `under-capacity`, an idle `primary` computer is skipped by the idle sweep unless `pressure.ReclaimPressure` is true (warmness_policy.go:231), and under the sustained signal that is true only when the sustained window is full (ownership.go `checkIdleOwnerships`, uses `SustainedPressureState().Sustained`). That needs MemAvailable < floor AND memory PSI avg60 > `MaxMemorySomeAvg60` for 4 consecutive 15 s samples, one computer at a time, 3 minute cool-down. At 13.1 GiB available, never.
  - Even under pressure, a candidate must be idle for `PRESSURE_RECLAIM_MIN_IDLE=30m`, not busy (fails closed on any non-200 /health), not held, not protected.
  - Alternatives that would also keep it resident, all checkable from vmctl health: the guest busy probe answered busy; `LastActiveAt` was refreshed by an API-key request (PR-09 says key requests refresh the idle clock); the computer is held.

## 3. Why b@c's measured need is ~7.8 GiB, and whether RSS shrinks

- **Configured size:** every non-platform computer boots 4 vCPU / 8192 MiB (node-b.nix:1647-1648). Platform-shape (4096 MiB) applies only to `public_platform` / the Universal Wire owner (ownership.go:1965). The paper is an 8 GiB guest (balloon-stats doc, vm-1669020a 8,093 MiB at 07:50 10-22; the 8069 MiB VM today is almost surely it).
- **Why RSS reached the guest size (PROVEN mechanism, HYPOTHESIS for b@c):** a guest's host RSS is every page it ever touched and has not freed back through the reporting device. Page cache is not free, so a build or a large Dolt read that fills guest cache pushes RSS to the guest size and it stays. Receipts: paper at 8,093 MiB 14 minutes after a cold boot with ~5 GiB of it reclaimable guest cache (balloon-stats doc, 07:41-07:50 evidence); paper page cache 4,747 MiB, 4,210 MiB of it the Dolt store (ledger 06:25 10-22); 12.9 GB snapshot on an idle test computer. For b@c specifically, its recent engineering capsule builds are the likely cause. To confirm: vmctl health memory peak for b@c, or the balloon stats reader for b@c (it is the one computer that has stats on): `GET localhost:8083/internal/vmctl/memory/balloon`.
- **Does RSS shrink after a spike?** Partly.
  - Anonymous memory the guest frees does return: ledger 10-22 21:26, burst peak 3,614 MiB to idle end 2,100 MiB, host RSS fell 1,614.7 MiB for 1,288.2 MiB freed. Free page reporting needs 2 MiB blocks (page_reporting_order 9).
  - Page cache does not: DAMON_RECLAIM on two test computers returned nothing in a 16 minute idle window (ledger 13:06 10-22); capsule teardown reclaims only capsule cgroups.
  - Guest hibernate (snapshot) drops RSS to zero, then a wake reads back ~0.3-0.4 GiB lazily. So a hibernate-wake cycle is the only thing that reliably resets a guest's RSS today.
  - The recorded peak persists on the ownership after stop, so admission keeps charging the old spike: `finish(true)` resets the *in-flight* peak (`peakReset`, host_admission.go ~292) but `estimateNeedWith` reads the ownership's last stored value until the new run's samples overwrite it.

### 6.3 Does a hibernated computer wake on a request? (the 10-14 "operator hibernate" caveat)

- Code: the hibernate reason (`operator`, `idle`, `pressure`) is only recorded in `StoppedBy` (ownership.go:3041); the resolve path starts any `VMStateHibernated` ownership that is not held (ownership.go:2220-2240) through `startExistingVM`, which runs admission (ownership.go:1580) and then `resumeFromSnapshot`. So a session-authenticated request wakes idle, pressure and operator hibernates alike. The 10-14 502/503 was seen with the probe's request path; the later R5 reading explains it: **a bearer (API key) request never wakes a computer** (`internal/proxy/api_key_computer_authority.go:166-183`, by design; only `POST /api/computers/{id}/lifecycle/start` does). I did not find a code branch that treats `operator` differently; HYPOTHESIS that the 10-14 caveat was the bearer rule, since the probe used a key. A browser-session wake test of an idle hibernate is not in the docs I read.
- **The wake is itself subject to admission.** A hibernated computer whose last measured peak is large is refused at wake with the same `host_memory_pressure` 503. So hibernating does not make a computer cheaply wakeable when the host is near the line; this is exactly the b@c case in reverse.
- **Snapshot wakes rarely happen at current deploy cadence.** 10-22 R1: 8 hibernates in 58 h, **0 resumed**; the 2 wakes were cold boots on `launch_config_mismatch`. 76 deploys in 58 h (about one per 45 min) and every deploy changes the guest image path in the launch-config hash. The only snapshot resume in 60 hours was FP0's, woken 1 s after hibernating to beat the next deploy (wake_to_healthy 351 ms). So "hibernate and wake in ~0.1-0.4 s" is proved but is not what users usually get on staging today; they get a cold boot (about 10 s, ~1.2-1.4 GiB resident, and a crash-style boot). L20 (snapshots surviving deploys, unbuilt) is what fixes that.

### 6.4 Answer to the owner: "why is the memory snapshot 8 gigabytes? Can't it be sized to what it's actually using?"

Short answer: yes, and that is the Diff snapshot lever, which is built and switched off.

- Why 8 GiB: the guest is configured with 8 GiB of RAM and Firecracker's default (Full) snapshot writes the whole range, including pages the guest never touched (zeros). The memory file shows `size=12884901888 blocks=16777216 x 512` (R3): 12 GiB long because of the 4 GiB hotplug range (a hole), 8 GiB allocated. A typical cold guest actually holds only **14-17% resident (1.15-1.37 GiB)** (R5); a restored one 2.8-6%.
- What it really costs today: on disk, btrfs zstd shrinks the zeros, so the real footprint is **0.74-1.5 GB** per snapshot (8 of 9 readings; outliers 2.4 GB and 4.0 GB), 628 MiB under the jailer. The `8 GiB` figure is the logical/allocated size. The remaining cost is **time and I/O**: Full hibernates take 5.6-10.4 s (R1, R6) and write 8 GiB through the page cache to be compressed.
- The sized-to-use version: Diff, snapshot_diff.go. Firecracker 1.13+ finds resident pages with `mincore(2)` (dirty tracking is off) and writes only them into a sparse file of full length; holes read as zero, so the file is a complete image and the existing load path is unchanged. It would write about **1.2-1.4 GiB** instead of 8 GiB. My estimate (not measured; the design's gate is "a hibernate under 2 s"): about 1-1.5 s by proportion. Disk bytes after compression would not change much (Full already compresses to about 0.8-1.0 GB); the gain is write time, PSI, and the honest `st_blocks` budget (1.2 GiB vs 8 GiB allocated, snapshot_diff.go failure mode 6).
- **Status of the lever:** code complete and reviewed (RES-13 L3a, commits 19f7f483d..f6fafa8ec; four review accepts; 12 mutants run, 10 killed, survivors then pinned by tests); shipped inert in deploy Q (ledger line 369); never turned on, so there is **no staging proof**, only unit tests. Switched-off inventory B9: "never turned on".
- **Guards that make it safe (all must hold or it takes Full):** selected by `VM_SNAPSHOT_DIFF_ONLY` (empty today); `VM_SNAPSHOT_TYPE=diff`; the Firecracker process was cold booted by this vmctl (`ColdOrigin`); Firecracker at least 1.15.0 (v1.17.0 passes); guest memory cannot swap (`VmSwap 0` and an ancestor cgroup `memory.swap.max 0`: vmctl unit 0 at node-b.nix:1506, VM slice :1422); every guest mapping `THPeligible 0` (read as 0 on staging, R5); the file length equals mem plus hotplug MiB (hotplug is off now, so 8192 MiB). Failure falls back to Full in the same pause, then to the kill path.
- **The catch, restored guests:** after a snapshot resume the guest's RAM is a private mapping of the old snapshot file, mostly clean file pages the kernel may evict, and `mincore` misses evicted pages. A restored guest therefore must take Full (`ColdOrigin` false), so L3a only helps the **first hibernate after each cold boot**. L3b (diff of a restored guest, rebased onto the old file with `snapshot-editor edit-memory rebase`; `snapshot-editor` is installed, R4) is unbuilt, and is gated on a week of class:test Diffs.
- **To turn it on everywhere (all red, snapshot format):** (1) one-computer proof per the design's steps: cold boot a test computer, write 1 GiB random to tmpfs, hash, hibernate with `VM_SNAPSHOT_TYPE=diff` and `VM_SNAPSHOT_DIFF_ONLY=<id>`, record `snapshot=ms`, `stat` of `snapshot/mem`, PSI, wake via `lifecycle/start`, verify hash and desks, repeat with full, and check a second hibernate of the resumed computer logs Full; (2) widen to `class:test` for a week with no `snapshot_files_missing` or post-wake health failure; (3) L3b; (4) then L4 (idle 30 m -> 10 m, config only), which the design gates on L3 being on for every class. Rollback at any step: empty the list or set `full`; a pending Diff is refused at load (`diff_lever_off`) and cold boots; a git revert still loads a cold-origin Diff correctly. Mutation class: red.
- **Does diff change the density story?** Modestly on its own. The main wins are shorter hibernates and a cheaper path to a 10 minute idle timeout. It does nothing for the b@c refusal (admission charges peak RSS, not snapshot size) and nothing for deploy-voided snapshots (L20), which currently decide whether a hibernate ever becomes a fast wake.
