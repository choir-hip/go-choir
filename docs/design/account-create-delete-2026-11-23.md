## A. Creation today

- Routes (`cmd/auth/main.go:90-131`): `/auth/register/begin` and `/finish`, login begin and finish, device begin, lookup, approve, token, recovery, email sign-in. All are classed for rate (`rate_limit.go`).
- `register/begin` (`internal/auth/handlers.go:605`) takes only an email, checks its shape, creates a `users` row if the email is unknown (`:640-651`), then opens a WebAuthn ceremony. It requires a **platform authenticator** and asks for PRF (`:681-690`). **No email verification** and no invitation gate [src]. An existing email with a passkey answers 409 (`:670`). An abandoned ceremony leaves a `users` row with no passkey.
- `register/finish` (`:845`) verifies, stores the credential, nudges the numbered mail address (`nudgeNumberReconcile`, `:962`) and issues a passkey session.
- **The only gate** is `AUTH_REGISTRATION_CAP` (`registration_cap.go`): users holding a passkey, checked at begin and again at finish, fail closed, 403 `registration_waitlist`, email put on `registration_waitlist`. In `nix/node-b.nix:~900` it is a comment ("FP0 sets it"), so **no cap is set** [src: the comment; I could not see the deployed value, **unconfirmed**]. The web frontend never mentions the waitlist code (grep of `frontend/src` found nothing), so a refused stranger sees a generic error.
- Bounds on strangers: `register/begin` and `login/begin` 10 a minute per IP; finish and device begin and lookup 30; device token 60 (`rate_limit.go:30-50`, `device_login.go:40`). Relying party `choir.news`, one origin (`nix/node-b.nix:887-888`).
- **Computer: created lazily, not at sign-up.** The web calls `prewarmAuthenticatedComputer` after sign-in (`frontend/src/lib/auth.js:418`), which hits `/api/shell/bootstrap` and makes the VM. A key-only account (the phone) gets one at its first owner-wide read of `/api/compute/status` or any route that resolves a computer (`internal/proxy/api_key_first_computer.go:1-60`). **[infer]** The phone's first signed-in calls (edition lookup, computer page) therefore create a VM within seconds of the first sign-in.
- Cost of one computer: a Firecracker VM of 4096 MiB (`nix/node-b.nix:1623`, `VM_MEM_MIB`), a sparse 32 GiB `data.img` (`internal/vmmanager/manager.go:78`), a store, tape segments, snapshot chunks, a numbered mail address. Hibernation after 10 idle minutes writes a snapshot (`docs/system-map.md` section 2). Admission refuses starts under a 32 GiB floor or when memory fails; "make room" hibernates up to 3 idle computers. Real numbers: one host, 476 GiB disk, fell to 44 GiB free on 11-22; a hibernated test computer used 8.4 GiB with a 19.8 GiB image (`docs/definitions/choir-storage-efficiency-2026-11-22.md:15-20`). **A fresh computer's true footprint is not measured in any doc I read [unconfirmed]**; with hundreds of testers the binding limits are host memory admission and disk, not the auth service.

## B. Creation inside the app

Facts all options share. The app holds only a bearer key from the device flow. Approval needs a **passkey session** (`device_login.go:395-420`; an email session or a key is refused) and mints a full-access key, owner acts included (`deviceGrantText`, `:294`). Today the approval page (`DeviceApproveRoute.svelte`) signed out offers only "Sign in with passkey" plus an email field; there is no create-account path in it. `AuthEntry.svelte` already has Create account and Sign in tabs, but it is the web shell, not the device page.

**Option 1: the system sheet shows create-or-sign-in.** The approval page gains a register view (reuse `registerPasskey` and `createPasskeyFromOptions`, `auth.js:81,115`), shown when signed out. After register finish the session cookie exists in the sheet, `afterSignIn()` runs the lookup and the person approves; the device flow and `return` hint are untouched.
- Server change: none required. Optional: a distinct "create" copy and waitlist message.
- Exact/shared code: a "Create account" action beside Sign in that opens the same sheet (`signin-attempt.ts` already begins an attempt); an `intent=create` query hint, never read from the callback.
- Native: none. The CLAUDE.md contract is kept as is.
- Does a passkey made in the sheet work in Safari? **[memory]** `ASWebAuthenticationSession` renders Safari content, supports WebAuthn on iOS 16 and later, and a non-ephemeral session shares Safari's passkeys and cookies; the passkey is stored in iCloud Keychain scoped to the RP ID `choir.news`, so it should appear in Safari. `docs/reference/exact/auth-session.md` states non-ephemeral shares passkeys [src: Exact source `AuthSession.swift`, per that page] and is **[unrun on a device]**. Whether creation (not only use) succeeds in the sheet, and whether the sheet insists on the "platform authenticator required" setting, is **unconfirmed** and is the one fact to test first on a device. The simulator drives no sheet (`auth-session.md`), so this is device-only.
- Class: orange (frontend page and copy, no auth change) unless the server changes. Review: one seat. Size: about 1 day including a proof on the paid-team phone.

**Option 2: native passkey ceremony in the app.** Exact has a first-party `@exact/passkeys` package (`create`, `get`, grant `auth.passkey <rp id>`; `.exact-src/packages/passkeys/exact.json`, read in another lane's checkout at the same pin `f53347503`) [src]. It needs: Associated Domains `webcredentials:choir.news` on an explicit App ID profile (the wildcard profile cannot carry it, per the package's own checklist) [src]; an `apple-app-site-association` file at `https://choir.news/.well-known/apple-app-site-association` listing each app id (`<team>.news.choir.autoradio` and the `.lab.one` development id), served as JSON without redirect [memory for the format; `frontend/public` exists and Caddy sends unknown paths to the proxy (`node-b.nix:754`), so serving is a small change but **[unconfirmed]**]; a dev build must use `?mode=developer` and Apple's CDN can lag for hours [src checklist]. Server: `register/finish` today returns cookies, not a key, and the ceremony's `origin` for a native client is Exact's own open question (QUEUE: "record the Apple origin") [src], while `AUTH_RP_ORIGINS` is only `https://choir.news`. A new key-minting route is needed (the Exact page says so: red) that approves a device authorization in the same transaction as the register finish, or the app opens the sheet afterwards anyway.
- The "native call" is Exact's package, not new Swift in `mobile/AutoradioKit`, so the contract's "only voice is native" rule is met by using the shared framework; the reason written beside the grant would be "the platform's passkey sheet is a system API". **[infer]** that this satisfies the rule; the owner wrote "passkey sheet in app later".
- Class: red twice (auth routes, key minting) plus a capability and profile change. Two review seats. Size: 5 to 8 days, with risks in Apple's CDN lag, the origin string, the profile, and no simulator proof.

**Option 3: anything else in Exact's auth-session page.** `openAuthSession` with an https callback needs a domain association (the same AASA) and gives nothing over the private scheme. Email-code sign-in exists on the server (`email_signin.go`) but an email session may not mint keys or approve devices, so it cannot create a phone key. A review-code path (research doc 4B) is a second sign-in method: red, and not an account creation path.

**Recommendation: Option 1 now; Option 2 afterwards.** It meets the owner's words (the account is made in the app, the same account as choir.news), and Apple's rule is about deletion being in the app, not creation being native [memory; the research doc quotes the page, section 2]. It lands soonest and needs no profile change. It also fixes the reviewer problem: a reviewer creates their own account with any address (email is unverified), so no demo passkey account is needed, *provided the registration cap is open*. Risk: the sheet shows a web page, which Apple accepts as in-app authentication for the developer's own system [memory]. Option 2 later, as polish.

**First run.** Signed out the radio and paper play (built). A spoken ask, a personal page (mail, files, notebook, takes, settings) or "Sign in" shows one card: "Create an account" and "Sign in" (both open the sheet), "Not now". After sign-in the account has no edition: `onboarding.ts` already offers "Make it yours" (voice setup, mic, topics) when `lookupEdition` finds none (O11, `onboarding.ts:~284-292`), so the new account lands on that page; the microphone is asked there, not at Play. The first computer is created by that first lookup; say "Setting up your computer" on the card while the first call is slow [infer].

## C. Deletion

**What 5.1.1(v) needs in practice** [memory plus research doc section 2]: deletion starts inside the app (a link to a page that completes it is allowed); it deletes the account and its associated personal data, not only deactivates; a confirmation step is allowed; Apple's page allows saying how long it takes, and permits retaining data that law requires with the person told [memory, **unconfirmed wording**]. A grace period is tolerated if stated; "contact support" is not enough.

**Proposed design**, all of it red, on the drill account only:
1. **Start.** Settings > Account > Delete account. A card states what will go (account, computer and everything on it, takes, mail address) and the time ("within 24 hours; some copies for up to 30 days"), then opens the sheet at `/account/delete?return=...&state=...` (same hint rules as the device page).
2. **Confirm with a fresh assertion.** The page forces a *fresh* passkey login (`login/begin` and `finish` with an `intent=delete` challenge type; session age under 5 minutes), shows the email and the same facts, and requires a typed confirmation. A bearer key cannot delete (it holds `owner:acts` but approval-class acts are passkey-only today), so the sheet is the only confirmer; Option 2's native assertion could replace it later.
3. **Server accepts, then acts durably.** One transaction writes a `deletion_jobs` row (auth.db) with state `requested`, revokes all sessions and keys at once (the phone's next call is refused, and its existing "key refused" path leads to the ordinary sign-out and wipe). The job is a state machine that survives restarts and resumes by row, not by boot memory (a planned or crash restart re-reads the row; this is a standing obligation, not a resume of agent work, so it fits the Restarts rules [infer]).
4. **Steps**, each idempotent and recorded as counts and ids only: refuse (paper account, owner account, `critical_protected` or `public_platform` computers, anything in `computer-tiers.json`'s protected lists, any computer under a hold or live capsule) → unpublish or anonymise published objects → delete takes → purge mail → vmctl remove and `DestroyVMState` → corpusd tape purge with `NoArchive: true` (a new apply path for a user request; the sweep's own minimum quiet window, 24 hours, still applies, and a refusal that waiting does not clear is named in the receipt after 48 hours) → revoke gateway identity → delete the `users` row (cascade) → write the receipt. The receipt holds the job id, counts per kind, times, and a hash of the user id; no email, no content.
5. **Proved** on the drill account (`d@e`, ring R0) only; adversarial refusals (paper, owner, a held computer) as unit and staging tests, never against those accounts.

**Owner decisions, with conservative defaults:**
- Published stories and takes: remove, anonymise or keep. Default: remove takes; **keep a published story but detach the author** (tombstone the author fields) because other stories cite it, and say so in the card. Removing breaks citations; the paper's own record is evidence.
- Grace period. Default: immediate revoke of every session and key, then a 72 hour hold before the irreversible purge, cancelable by signing in again, because an accidental deletion cannot be undone and Apple accepts a stated delay [memory]. The research doc's default is immediate; the trade-off is more retained data against the cost of a mistake.
- What is retained: the tape head row and tombstone (no content), the deletion receipt, abuse logs 30 days, anything law requires. Default: exactly those.
- Public permalink after deletion: 410 "removed by its author" for takes; for anonymised stories the story stays, author blank [infer].

## D. Abuse and capacity

- A stranger can cause: a `users` row per begin (10 a minute per IP, so 14,400 a day per address if unpaid for; abandoned rows are never swept [infer]); a passkey, a session, a numbered mail address; and, once signed in, a **4 GiB VM** on first use plus model calls, searches and storage. I found **no per-account quota on model calls, searches, VM time or disk**; the gateway limits are global or per computer class (`gateway/jev_limiter.go`), the takes bound is 10 a day (`AUTORADIO-TAKES.md:70`). **Unconfirmed**: that grep was brief.
- Allowed bounds under the contract: bounds on what strangers can cause, owner spending caps, deadlines. Not allowed: limits on our own model calls.
- Recommendation: **testers get an account, not a computer, until they ask for something personal.** Create the VM at the first request that needs one (mail, files, notebook, a spoken ask that needs the computer, publish), not at sign-in. Today the phone's first lookup creates it; the lookup for the edition should be answered from the paper's public data without resolving a computer [infer: needs a code read of the route]. Meanwhile set `AUTH_REGISTRATION_CAP` to a number the host can carry (owner decision; the plan is the waitlist already built), and add the waitlist message to the sheet. Sweep abandoned user rows older than a day, and cap abandoned begins per email. Retention already removes ephemeral and test accounts by email domain or id prefix; use it for tester accounts the owner marks.
- Stronger and cheap: a light computer (smaller memory) is not available today as a tier [unconfirmed]; "none until asked" costs nothing to build compared with a new tier.
