## 0. The shortest honest summary

- Signing in, the account card, the shared client (`api.ts`) and the sign-out *orchestration* (`account.ts`) are already shared code, with a large test suite
  (`api.test.ts`, `account.test.ts`, `account-state.test.ts`, `app-signin.test.ts`). What is left in the four Swift files is: a **second reader of the key** (the voice
  turn's own HTTP client, `ChoirClient`), the **native half of sign-out** (stop audio, delete the Keychain items, run `AccountWipe`), the **native store registry** (`AccountWipe`)
  and **deck and audio wiring** that sits in `ChoirApp` and is not account code at all.
- The key already crosses into shared code's memory today: `api.ts:195-204` reads it with `store.get` on every request and builds the header in JavaScript (`api.ts:299`), and sign-in
  receives it in a JSON reply in JavaScript (`app-signin.ts:122-124`). So "the key stays native-only" is not the current state on either platform, and cannot be reached without also moving sign-in's finish request native.
- The station text says "the voice turn reaches the server through the shared client". For the live turn that is **not achievable as worded**: the turn is `POST /api/autoradio/turns`
  read as a server-sent stream as it arrives (`ChoirClient.swift:364-384`, `Choir/AutoradioDesk.swift:168`) and `docs/reference/exact/gaps.md:47` (row 36) records that shared code cannot read a POSTed stream as it arrives. What can be shared is the key's custody, the origin, the 401 handling and the sign-out; the streaming transport for the turn stays native, thin.

## 2. The key's custody: the central decision (owner-level)

### What is true now

1. **At rest**: one copy, in Exact's secret store (Keychain on Apple), written by shared code at sign-in (`app-signin.ts:47-52`, grants `app.ts:57-59`). Android: Exact's store (AES-GCM files wrapped by an Android Keystore key, `passkeys.md:65-68`); device proof of sign-in/relaunch/sign-out is **[unrun]** (`passkeys.md:82-83`).
2. **In memory, shared side**: the key is read on every request (`api.ts:195-204`), held in a local variable, in the header (`:299`), in `revoke` (`app.ts:131`) and `bearer` (`account.ts:287`). At sign-in it arrives in a JSON body (`app-signin.ts:122-124`). So the key is in JavaScript memory already.
3. **In memory, native side**: `ChoirClient.request` reads the Keychain per request (`ChoirClient.swift:353`); no cache.
4. **The key never crosses the bridge as a message.** Native reads the Keychain item itself; shared code never sends it to native, native never sends it to shared. Only `keystate`/`session`-style reads go through the store, inside shared code.
5. **Key properties on the server**: a key minted by the app's passkey finish has `AllScopes()` and **no expiry** (`internal/auth/app_ceremony.go:212-220`: `CreateAPIKey(ctx, user.ID, label, scopes, nil)`); it dies only by revoke or by the account's deletion (`internal/proxy/handlers.go:~700`, `accountAccessRevoked`); the phone never refreshes it (`api.ts:62`). Anything that reads it holds the account until someone revokes it. This raises the stakes of every copy.
6. Server contract the phone relies on: header `Authorization: Bearer choir_sk_...`; `X-Choir-Computer: <id>` on everything except `/auth/*` and `/api/compute/status` (`api.ts:306-308`, server `internal/proxy/api_key_computer_authority.go:23-52`); a missing, unknown, expired, revoked or account-deletion-pending key is **401** `{"error":"authentication required"}` (`internal/proxy/handlers.go:597-607, 657-720, 770-782`; agentcore repeats it `internal/agentcore/api_autoradio.go:172-174`); a key without the route's scope is **403** `missing required scope: ...` (`handlers.go:610-620`); revoke is `DELETE /auth/api-keys/{id}` and the key may revoke itself (`internal/auth/handlers.go:2098-2116`).

### Options

**(a) The key stays native-only; native makes every authed request for shared code.**
- Mechanism: shared `authedJSON/Text/Bytes/ToFile` become `native.later({op:'fetch', ...})` calls (the app module's `later`, JS to native: `docs/reference/exact/native-modules.md` "Calling convention"). Native holds the key, builds the header.
- Leaks if the JS context is compromised: the key cannot be copied out of the Keychain by script, but script can make any request through the bridge (a confused deputy), so for the attacker the account is as exposed as today for as long as the compromise lasts; after it ends, nothing remains. A stolen device backup exposes the same as today (one Keychain item).
- Cannot be pure: sign-in's finish reply carries the key into JS (`app-signin.ts:122-124`); keeping it out requires the finish request itself to go native, which moves the passkey ceremony's last step out of shared code (the ceremony is `@exact/passkeys`, shared). So the key is in JS at least once per sign-in.
- Costs: loses Exact's grant-checked `fetch`, `exactBodyTo`/`exactBodyFrom` (large files stay out of the heap: `reference.md:2553` in exact-src) unless rebuilt natively, and base64 for bytes over the bridge; native URLSession is outside Exact's `net.fetch` grants. **Android must implement it in Kotlin** and, because Exact's Android secret files are wrapped by a Keystore key only Exact's store holds (`passkeys.md:65-68`), Kotlin cannot read the shared store with a plain API: sign-in's `keepKey` would also have to go native. **Native lines**: ChoirClient stays (~200 of its 439, rebuilt for streams, bytes, files) plus a Kotlin twin; E6 would **add** native code, the opposite of the mission.
- Is it "voice or platform"? It is neither voice nor a platform need; it is a security preference. It needs an owner ruling to be an exception to "everything else is Exact".

**(b) The key stays in Exact's own protected storage; shared code is the only reader that touches it; native voice is handed the key.** Two shapes:
- **b1, push once into native memory** (recommended): after sign-in, and at each answer's start if native says it has none, shared code sends `{op:'turnKey', key, computerId, origin, gen}` to native; native keeps it in memory only (never writes it), uses it for the turn's requests, and drops it on `{op:'forgetKey'}`, on a generation bump, and at process death. Native stops reading the Keychain; `KeychainKeyStore`, `KeyStore`, the Keychain `computer-id` write and native discovery go. Android is the same op, so Kotlin needs no store access, and the turn transport is the only network code Kotlin owes.
- **b2, native asks shared code per request** (the "native asks shared code" pattern, `native-modules.md` heading "Native asks shared code"): fails for the live turn: shared code is read only while root resources run, has no push, and cannot read a POSTed stream (`gaps.md:47`). Also needs JS running with the screen locked, which is **[unrun]** (`docs/reference/exact/audio.md:131-140`, goal station E8). Reject for the turn.
- If the JS context is compromised: it holds the key today as well; b1 adds no exposure beyond what the shared client already has, and shortens native's exposure window nothing (memory holds it for the session). Rendered content: the reader's web pages run in a separate native view (`web-page` package view, `native-modules.md:43`) not in the data module's context, and mail is parsed by `mail-sanitize.ts`/`reader-parse.ts` (hostile-input tests: `reader-parse-hostile.test.ts`); the context is therefore compromised by a parser or dependency bug, not by a page's script **[inference]**.
- Backup: the item is `...ThisDeviceOnly`, no sync (`passkeys.md:55-56`). What an encrypted local backup of an unlocked, jailbroken device exposes is not in the repo **[not verified]**; b1 changes nothing there.
- What Android must implement: the same `turnKey`/`forgetKey` ops and the turn transport (SSE POST) in Kotlin, with no Keystore code. Shared code already has the Android sign-out path with read-back (`account.ts:403-410`, `account.test.ts:69-132`).
- Native lines remaining: a turn transport of about 120-150 lines (request build, same-origin check, SSE line reader, error map; roughly the current `request`, `send`, `postEventStream`, `error`, `SameOrigin`) plus the key holder (~30). Deleted: `KeychainKeyStore`, `KeyStore`, `FileKeyStore`/`OverlayKeyStore` (unless the replay tool needs them), `LegacyKey`, `ChoirSignIn`, discovery (~35), `PathSegment` (shared has `segment`).
- New risk: **cold start with no JS**: until shared code pushes the key native has none, so a voice turn started by a remote command with JS not yet booted fails closed (no key, no turn). It does not fail open.

**(c) What Exact offers natively** (cited, none is a drop-in):
- `secret.keep <name> user-presence` (also `biometry-any`, `biometry-current-set`, `device-credential`): `store.get` throws `InvalidAccessError` while locked; `await store.unlock(name, {reason})` shows the sheet; `await store.protect(name)` turns an `optional` lock on without a prompt on iOS, iPadOS, Android and provisioned macOS builds (`contract-for-agents.md:1551-1561` in exact-src). This would protect the key against a stolen unlocked-device read of the file, but a hands-free voice turn cannot meet it: the repo already ruled `user-presence` out ("a lock the voice code cannot meet", `passkeys.md:64`). It could protect only a **non-voice** copy, which does not exist (one key serves both).
- `{secret:NAME}` header substitution: a declared contract resource may send a kept secret in a header "so a page never sees it" (`contract-for-agents.md:1364, 1371`; preloads, `reference.md:501`). It covers declared GET/POST-JSON sources, not the data module's `fetch` with `exactBodyTo`/`exactBodyFrom`, streams, PUT bytes or the revoke. It could remove the key from JS for simple reads, at the price of two request paths; not enough for E6.
- `store.keepKey/store.key`: a platform-kept P-256 key pair (`contract-for-humans.md:915`). A device-bound signing key would let the server stop trusting a bearer string, but it needs server work (accepting signed requests) and is outside E6 **[I read only the table row, not the API]**.
- Web `secret.keep` is origin-readable `localStorage` (`reference.md:6429`): irrelevant to the phone, relevant only if a web build ever signs in.

### Recommendation

**(b1)**, conservatively staged: the key stays where it is (Exact's secret store, Keychain/Android store); shared code is the only reader; native receives the key by an explicit, generation-stamped push into memory and never reads or writes the Keychain. One reason: it is the only option that gives Apple and Android **one** code path with **no** native secret-store reader (Kotlin cannot read Exact's store with a plain API, `passkeys.md:65-68`), while adding no exposure the shared client does not already have, and it shrinks native to a streaming transport that has a stated platform reason (gaps.md:47; the turn runs with the screen locked).

**What would change it**
- Choose (a) if the owner rules that a script-level compromise must not be able to copy the key (it adds native code and a Kotlin twin).
- Choose "keep the native Keychain read on Apple" (today) if the cold-start-no-JS window of b1 is unacceptable on a device (E8's ten-minute locked run, `goal file E8`, shows JS frozen when the voice needs a turn).
- Choose (c) `user-presence` only if the owner accepts a hands-free turn that asks for Face ID (it would defeat hands-free).
- Re-open everything if the server gains short-lived or device-bound keys (today's key never expires, section 2 item 5): then custody matters far less.

## 5. What I could not determine, and where documents and code disagree

Could not determine
1. Whether URLSession drops the `Authorization` header on a cross-host redirect, and whether `.shared` follows redirects for these requests in practice. Not in the repo; I did not run anything. I5 exists because the Swift code does not rely on it either way.
2. Whether Exact's door answers `null` (not an error) for `store.get` after an `await` in a turn with no bound store. The claim is in the unlanded lane's problem record (`origin/lane/move-b`, `door.rs:45-53`) and in the account-boundary assessment ("the store answers only in an answer's first turn"); I did not read Exact's source. If true, main's `api.ts:111-126, 195-204` has the hazard and `reconcile` could take an "absent" for a sign-out (record item 2).
3. Whether JavaScript is running while the screen is locked at the moment a voice turn starts. `audio.md:131-140` derives it from source and calls it **[unrun]**; station E8 measures it. It decides whether b1's cold-start window matters.
4. What a backup of an encrypted, jailbroken or unlocked device exposes of a `...ThisDeviceOnly` item. Not in the repo.
5. Whether `RemoteHost.allows`, `FileKeyStore` and `OverlayKeyStore` have any non-test caller beyond `autoradio-replay` (`main.swift:50-56`); my grep found none for `RemoteHost`.
6. Whether the owner wants several accounts in one install (words of 2026-11-21 in `docs/problems/account-boundary-three-approaches-no-convergence-2026-11-23.md`). The unlanded lane `account-boundary-l1` (15 commits, 3,178 insertions, 56 files) built a "world" closed by the boundary moving; its intent is: derive the account from key and record before every answer, make every I/O choke point inert for a closed world, give module state to the world, and make the Texture themes two stores. Main instead has the stamp/marker/`decide` table (`account.ts:151, 227`) and the generation counters. This design does not assume l1's boundary and adds one account per process.
7. Whether the iOS `console.log` and `voice-choice.json` are per-person. I read only the file headers.
8. The proof that a device sign-in, relaunch, authed read and sign-out work on Android: `[unrun]` (`passkeys.md:83`).

Where documents and code disagree
- Goal file E6 says the voice turn "reaches the server through the shared client"; `gaps.md:47` and the audit (`docs/evidence/exact-conversion-audit-2026-11-24.md:72`: "the desk stream needs the WebSocket or GET-with-ticket route first (server work, orange)") say the stream cannot be read by shared code. This design keeps a native streaming transport.
- `docs/reference/exact/passkeys.md:60-62` says the Texture editor and the notebook in Swift call the server and read the key; they are shared now (`L/texture-edit.ts`, `L/notebook-run.ts`; `ModelsEntry.swift:10` says shared). The page is stale and E6.5 edits it.
