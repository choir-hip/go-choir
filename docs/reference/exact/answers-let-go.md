# An answer is let go: fetches after an await

A source's answer (a resource, a derive, a mutation's send) may `await` and then fetch or call a native module, but only while that answer is still the one asked for. When the same resource is asked again with new arguments (a pulse every second), or a mutation is sent again, the older answer is **let go**: its next fetch is refused with "the answer was let go before this fetch" (`js/src/fetch.js`, `if (call.letGo)`; the same rule for the host's path in `host/web-js/ts-fetch.js`, `letGo` and `answers`, line 352). A fetch begun from work no answer waits for fails as "called from background work" (`js/src/fetch.js`, `call === background`) or "outside an answer" (the `!call` branch above it), and `native.call` likewise (`js/src/prelude.js`, `currentCall === background`). So a resource that is asked often must only read (one call, no chain of them) and say what work is due; the work, with its several awaited calls or a long fetch, belongs in a mutation, which stays until it is done. Every `void asyncCall()` is such background work. In this app: `radioPulse` reads, `radioHold` and `radioWrite` work (`mobile/AutoradioLab/radio-bridge.ts`), and `radio-pulse-rule.test.ts` fails when the pulse fetches or pumps, or a new `void` call appears unreviewed.
