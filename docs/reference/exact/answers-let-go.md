# An answer is let go: fetches after an await

A source's answer (a resource, a derive, a mutation's send) may `await` and then fetch or call a native module, but only while that answer is still the one asked for. When the same resource is asked again with new arguments (a pulse every second), or a mutation is sent again, the older answer is **let go**: its next fetch is refused with "the answer was let go before this fetch" (`js/src/fetch.js`, `if (call.letGo)`; the same rule for the host's path in `host/web-js/ts-fetch.js`, `letGo` and `answers`, line 352). A fetch begun from work no answer waits for fails as "called from background work" (`js/src/fetch.js`, `call === background`) or "outside an answer" (the `!call` branch above it), and `native.call` likewise (`js/src/prelude.js`, `currentCall === background`). So a resource that is asked often must only read (one call, no chain of them) and say what work is due; the work, with its several awaited calls or a long fetch, belongs in a mutation, which stays until it is done. Every `void asyncCall()` is such background work. In this app: `radioPulse` reads, `radioHold` and `radioWrite` work (`mobile/AutoradioLab/radio-bridge.ts`), and `radio-pulse-rule.test.ts` fails when the pulse fetches or pumps, or a new `void` call appears unreviewed.

## Work shared between answers: share the value, never the promise

Read against the pinned prelude (`f53347503`), 2026-11-25. Once an answer is let go its fetches and native calls in flight are rejected and new ones refused (`js/src/prelude.js:997-1034`), a timer it arms throws (`timerOwner`, `:1352-1366`), and the timers it had armed are DROPPED: they never fire and whatever awaits them stays pending (`timers.drop`, `:1041`; `js/src/time.js:234-238`). Every step of an async function runs as the answer that called it (`__exact_async_context`, `:230-241`), so a promise one answer started belongs to that answer however many await it. An answer that awaits such a promise and has nothing of its own in flight fails "the answer is pending on nothing" (`:719-752`); an answer with a timer of its own armed is asked again at that timer instead. So: never keep a promise where several answers can await it. Work done once for everyone belongs to an answer nothing lets go (a resource with constant arguments, asked again only by a declared `refresh`/`refreshes`), and the others wait for its VALUE with a timer of their own (`mobile/AutoradioLab/account.ts` `awaitSettled`); a read several answers want may be joined, but a joiner whose shared read was refused reads for itself (`api.ts` `joinOrRedo`, reads only, never a write); and a refusal (`api.ts` `isRefusal`) is never kept as a fact. `mobile/AutoradioLab/shared-promise-gate.test.ts` fails for a new kept promise; the Bun model of these rules is `mobile/AutoradioLab/testkit/exact-answers.ts`.
